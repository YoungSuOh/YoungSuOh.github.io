결제 시스템 설계

장애 상황에서도 정합성과 추적 가능성을 보장하는 결제 도메인 설계

🎯 설계 목표

이 결제 시스템은 단순 결제 처리가 아니라, 장애 상황에서도 정합성과 추적 가능성을 보장하는 것을 목표로 설계하여 다음과 같은 문제를 해결하고자 하였다.

  1. 중복 요청으로 인한 이중 결제 방지
  2. 결제 도중 장애 발생 시 재처리 가능 구조
  3. 모든 금액 흐름의 추적 및 감사 가능성 확보
  4. 결제 상태와 비즈니스 상태의 명확한 분리
  5. 환불, 부분 결제 등 확장 가능한 구조

설계 원칙

1️⃣ 멱등성을 시스템 레벨에서 보장

  • 단순히 if(status == SUCCESS) 체크 ❌
  • Idempotency Key를 외부 입력으로 받아 요청을 식별하고, Payment / Transaction에 DB Unique 제약 적용하여 단순 상태 체크가 아니라 DB 레벨에서 중복 차단

즉, “같은 요청은 DB가 물리적으로 한 번만 저장되게 만든다”

예시 상황

  • 작성한 코드가 다음과 같다면 
    if (payment.status == SUCCESS) {
    return;
}
  • 아래와 같은 상황이 발생했다면 둘 요청 다 SUCCESS 이전 상태 → 중복 결제 발생 
    사용자가 결제 버튼 클릭
→ 네트워크 끊김
→ 사용자가 다시 클릭
→ 서버에는 동일 요청 2번 도착 => 결제 2번 됨 (대참사)

따라서 Idempotency Key + DB Unique 제약을 통해 중복 결제를 방지

idempotency_key = "user123-order456"
  • 클라이언트가 생성해서 보냄 (같은 요청이면 항상 같은 key)
  • Payment 테이블에서 UNIQUE (idempotency_key) 를 통해 제약 조건을 걸어 “중복을 ‘코드’가 아니라 ‘DB’가 막는다”

2️⃣ 결제 도중 장애가 발생했을 때

결제 시스템은 “끝까지 정상 실행”을 가정하면 안된다고 생각한다. 왜냐하면 여러가지 이유로 결제 도중에 오류로 인해 실패하여 데이터의 정합성을 보장하지 못하는 일들이 발생할 수 있기 때문이다.

  • 서버는 중간에 죽고
  • DB는 커밋 전에 터지고
  • 네트워크는 응답을 날려버려

따라서 시스템은 다음과 같은 질문에 답을 해야 한다. → “이 결제는 이미 처리됐나, 다시 처리해도 되나?”

따라서 상태가 아니라 기록(Transaction)을 기준으로 판단하게끔 설계를 해야 한다고 생각한다.

  • PENDING → 미완료 (재처리 대상)
  • SUCCESS → 완료
  • FAIL → 실패

예시

  • 상황 1 : 서버가 응답 전에 죽은 경우 
    1. 결제 요청
2. Wallet 차감 성공
3. Transaction 생성 성공 (PENDING or SUCCESS)
4. 서버 죽음 (응답 못 보냄)
    • Payment 상태 = PAYING 이라 다시 결제하면 중복 결제 가능
    • 만약 Transaction 기반이면 
      Transaction:
- amount = 3000
- status = SUCCESS
      SUCCESS 이므로 재처리가 필요없음을 판단 가능
  • 상황 2 : DB 커밋 직전에 터짐 
    1. Payment 생성
2. Transaction 생성 (PENDING)
3. Wallet 차감 시도
4. DB 커밋 전에 장애 발생
    • Payment 상태 = PAYING 라 어디까지 로직이 실행됐는지 알 수 없지만 Transaction 이 PENDING 이라는 정보를 알면 재처리 대상으로 올바르게 처리 가능
  • 상황 3 : 네트워크 응답 유실 
    1. 결제 정상 완료
2. 서버 → 클라이언트 응답 전송
3. 네트워크에서 응답 유실
4. 클라이언트 재요청
    • 만약 단순한 상태 기반이라면 클라이언트가 새로운 요청 → 중복 결제

이처럼 Transaction 테이블을 두어 기록을 하게 되면, 여러 상황에서 장애에 대한 대처가 가능해진다.

3️⃣ 돈의 흐름은 반드시 기록한다

단순 잔액 변경 방식은 사용 ❌

정산 금액이 안 맞거나, 환불을 해야 하는 경우 → 감사가 진행되어야 하므로 Transaction 테이블을 통해 돈의 흐름을 추적한다.

- 고려 요소

  • 모든 돈 이동은 Transaction 1건
  • append-only 구조 ⇒ 기존 데이터 변경 없음

이를 통해 사용자 단위, 주문 단위로 감사가 가능해지고, 장애를 복구하기도 용이하다.

4️⃣ 결제와 돈의 흐름을 분리

다음과 같은 로직으로 단순히 구현하면 안된다

  • 결제 실패 = 주문 실패 ❌
  • 결제 성공 = 주문 성공 ❌

5️⃣ 확장 가능한 구조

초기 설계부터 고려

  • 부분 환불
  • 포인트 적립
  • 이벤트 기반 처리
  • 정산 시스템 연계

→ 모든 기능은 Transaction 기반으로 확장 가능

✅ 도메인 정의

🧍 User

  • 결제 주체 ❌
  • 단순 행위자 ⭕

💰 Wallet

  • 잔액 보유
  • 동시성 제어
  • 금융 주체

→ “돈은 여기만 있다”

📒 Transaction (가장 중요)

  • 돈 이동의 유일한 진실
  • append-only
  • 정산 / 감사 / 복구 기준

상태

PENDING → SUCCESS → FAIL
  • PENDING은 “미완료” (재처리 대상)
  • SUCCESS만이 정산 대상

💳 Payment

  • 결제 시도 단위
  • 사용자의 의도 표현
  • 실패/재시도 관리

상태

READY → PAYING → SUCCESS → FAIL → CANCELED
  • 재시도는 READY / FAIL에서만 가능
  • SUCCESS 이후에는 불변

📦 Order

  • 무엇을 샀는지
  • 얼마를 내야 하는지
  • 얼마나 결제되었는지

결제 처리 흐름 목표

1. 결제 요청 수신

2. Payment 생성 (Idempotency Key 기반)
   → 중복 요청 방지

3. Transaction(PENDING) 생성
   → 돈 이동의 시작 기록

4. Wallet 잔액 차감 (원자적)
   → 조건: balance >= amount AND version

5. 성공 시
   → Transaction → SUCCESS
   → Payment → SUCCESS

6. 실패 시
   → Transaction → FAIL
   → Payment → FAIL
