파티셔닝 & 샤딩

큰 테이블의 성능 한계를 해결하는 두 가지 접근 — 단일 DB 내부에서 나누는 파티셔닝과 여러 DB 서버로 분산하는 샤딩의 차이, Range/Hash/List 전략, 실무 문제(Cross-Shard Query·Join·분산 트랜잭션)와 적용 기준을 정리합니다.

DatabasePartitioningShardingScaling

파티셔닝

하나의 큰 테이블을 여러 개의 작은 테이블처럼 나눠서 다루는 것.

  • 데이터가 수천만~수억 건으로 커짐
  • 하나의 테이블/저장소에 몰림
  • 쿼리 느려짐 (특히 range, scan)
  • 인덱스도 비대해짐

⚠️ 그냥 쿼리 사용

SELECT *
FROM orders
WHERE created_at BETWEEN '2025-01-01' AND '2025-01-31';

→ 전체 테이블 스캔 ⇒ 성능 느려짐

✅ 파티셔닝 사용

orders_2024
orders_2025_01
orders_2025_02
  • DB 내부 구조가 다음처럼 나뉨
  • 이 상태에서 WHERE created_at BETWEEN '2025-01-01' AND '2025-01-31' 쿼리가 들어올 경우 DB가 자동으로 orders_2025_01을 참조 판단

1. Range Partition (범위 기준)

  1. 시간, 숫자 범위로 나눔 
    orders_2024
orders_2025
  2. 로그, 주문 데이터에 많이 씀
  3. 기간 조회 빠름, 오래된 데이터 삭제 용이

2. Hash Partition (해시 기반)

  1. key → hash → partition 
    user_id % 4 → 0, 1, 2, 3
  2. 데이터 균등 분산 → 특정 파티션 쏠림 방지

3. List Partition (특정 값 기준)

  1. 명확한 분리 
    region = 'KR' → partition A
region = 'US' → partition B

샤딩

데이터를 여러 DB 서버로 쪼개서 저장하는 것.

✅ 파티셔닝 vs 샤딩

구분파티셔닝샤딩
위치하나의 DB 내부여러 DB 서버
목적성능 최적화수평 확장
관리DB가 자동애플리케이션이 직접

❌ 샤딩 없을 때

  • DB 하나, users 테이블 1억 건 → 터짐 (CPU, I/O 한계)

✅ 샤딩 적용

Shard 1 → user_id 1 ~ 100만
Shard 2 → user_id 100만 ~ 200만
Shard 3 → user_id 200만 ~

여러 DB가 나눠서 처리.

1. Range Sharding

user_id 1 ~ 1000    → DB1
user_id 1001 ~ 2000 → DB2
  • 특정 구간 쏠릴 가능성 있음 (Hot Shard)

2. Hash Sharding (가장 많이 씀)

user_id % 4
  • 균등 분산

실무에서의 문제들

1. Cross-Shard Query

  1. 샤딩은 "어디 DB에 데이터가 있는지"를 특정 기준(샤딩 키)으로만 알 수 있음
  2. 예시) 샤딩 키: user_id 
    Shard 1 → user_id 1 ~ 1000
Shard 2 → user_id 1001 ~ 2000
Shard 3 → user_id 2001 ~ 3000
    • SELECT * FROM users WHERE user_id = 1500; → Shard 2에 있다는 걸 정확히 앎, 문제 없음
    • SELECT * FROM users WHERE age > 20; → "age가 20 이상인 유저가 어느 shard에 있냐?" 
      Shard 1
  user_id: 1,    age: 25
  user_id: 2,    age: 18

Shard 2
  user_id: 1500, age: 30
  user_id: 1600, age: 15

Shard 3
  user_id: 2500, age: 40

      → 모든 샤드를 다 봐야함 ⇒ 네트워크 비용, 응답 시간, 복잡도 증가

2. Cross-Shard Join

SELECT *
FROM orders o
JOIN users u ON o.user_id = u.id;
  • orders → shard A, users → shard B 일 경우 다른 DB 서버이므로 Join 불가
  • 따라서 비정규화로 테이블 데이터를 합치거나 다음과 같은 번거로운 Application Join을 해야 함 
    1. orders 조회
2. user_id 추출
3. users 조회
4. 코드에서 join

3. Distributed Transaction

Shard A → 돈 차감
Shard B → 돈 증가
  • 이와 같이 여러 DB 서버를 한 로직에서 참조하게 되면 데이터 정합성 깨질 확률 높음

🤔 언제 어느 조건에서 샤딩을 사용하나?

"한 DB로 더 이상 감당이 안 될 때 + 샤딩 키로 대부분의 트래픽을 처리할 수 있을 때"
WHERE user_id = ?
WHERE user_id = ? AND ...

대부분의 쿼리 호출이 샤딩 키로 호출되고 + 대용량 트래픽이라고 가정할 때 적용한다.
