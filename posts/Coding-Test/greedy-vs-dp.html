프로그래머스 문제 풀다 보면 매번 막히는 게 하나 있다. "이거 그리디로 풀어야 돼, DP로 풀어야 돼?" 이 노트는 문제 텍스트만 보고 둘을 가려내기 위한 정리다. 흐름은 단순하다 — 신호 → 가설 → 검증. 색은 두 가지로만 본다: 주황 = Greedy, 파랑 = DP.

⚠️

핵심 고민이 뭐냐면 — "지금 고른 최선이 전체 최선으로 이어지는가?"를 짧은 시간에 모든 케이스를 까보면서 판단하는 건 불가능하다. 그래서 사실 정답은 "모든 케이스를 안 본다"는 거다. 대신 반례 사냥과 교환 논법으로 판단한다. 이게 이 노트의 중심이고, 자세한 건 03번 섹션에서 다룬다.

01. 알고리즘 선택 가이드 — 큰 그림

그리디랑 DP는 둘 다 "최적해(최대·최소·최선)를 구하라"는 최적화 문제에서 나온다. 그래서 헷갈린다. 둘을 가르는 단 하나의 질문은 이거다.

💡

한 줄 요약: 지금 고른 선택을 나중에 후회할 일이 없는가? 후회 없음(되돌아볼 필요 없음)이면 Greedy, 후회할 수도 있어서 여러 선택을 다 따져보고 기억해둬야 하면 DP.

최적화 문제 만나면 머릿속에 이런 갈래가 그려져야 한다. 자세한 플로우는 섹션 05·13에서 다시 본다.

  • 최적해를 안 구한다 (조건대로 출력만) → 구현 / 시뮬레이션 / 완전탐색
  • 최적해 + 매 단계 한 가지 선택이 항상 정답 → 그리디
  • 최적해 + 어떤 선택이 정답인지 모름 → 다 해보고 결과를 저장 → DP

02. 그리디와 DP의 본질적인 차이

정의를 외우는 것보다 "두 알고리즘이 같은 갈림길에서 어떻게 다르게 행동하는가"를 이미지로 기억하는 게 낫다.

Greedy · 탐욕법

한 번 고르면 안 돌아본다

  • 매 단계에서 지금 가장 좋아 보이는 것을 고른다.
  • 고른 선택을 절대 번복하지 않는다. 미래를 안 본다.
  • 성립 조건 ① 탐욕적 선택 속성: 지금의 최선이 전체 최선의 일부가 된다.
  • 성립 조건 ② 최적 부분 구조: 부분 문제의 최적해가 전체 최적해를 구성한다.
  • 한 갈래만 보니까 보통 빠르다 (정렬 + 한 번 훑기).
DP · 동적계획법

다 해보고, 결과를 적어둔다

  • 한 단계에서 여러 선택지를 모두 고려한다.
  • 부분 문제의 답을 표/배열에 저장해 재사용한다 (메모이제이션).
  • 성립 조건 ① 최적 부분 구조 (그리디와 공유).
  • 성립 조건 ② 겹치는 부분 문제: 같은 부분 문제가 여러 경로에서 반복 등장.
  • 모든 갈래를 보되 중복을 제거 → 완전탐색보다는 빠르다.
🎯

두 알고리즘의 진짜 공통점과 차이:

공통점 — 둘 다 "최적 부분 구조"가 필요하다.
차이점 — 그리디는 "어떤 부분해를 골라야 할지 이미 안다" (그래서 하나만 고른다). DP는 "어떤 부분해가 최적인지 모른다" (그래서 다 계산해 저장하고 비교한다). 진짜 이 한 끗 차이가 전부다.

03. ★ "이 그리디가 맞나?" 검증하는 법

이 노트에서 제일 중요한 부분이다. 모든 테스트 케이스를 확인할 필요가 없다. 그리디의 정당성은 "케이스 점검"이 아니라 두 가지 기술로 판단한다 — ① 반례 사냥(실전용), ② 교환 논법(증명용).

기술 1 — 반례 사냥 (30초 안에 깨보기)

그리디 가설을 세웠으면 맞는지 확인하지 말고, 일부러 깨려고 시도하자. 단 하나의 반례라도 만들면 그리디는 탈락이다. 반례를 만드는 질문은 딱 하나다.

🔍

반례를 부르는 질문: "내가 지금 욕심부려 고른 선택이 미래의 선택지를 줄이는가? 줄인다면, 그 줄어든 선택지 때문에 나중에 더 큰 손해를 강제당할 수 있는가?" → 단 하나라도 그런 작은 케이스를 만들 수 있으면 그리디 ✗ → DP로 간다.

가장 유명한 반례는 거스름돈이다. 동전이 {1, 4, 5}이고 8원을 거슬러줄 때, 그리디는 큰 것부터 → 5+1+1+1 (4개). 근데 최적은 4+4 (2개). "큰 걸 먼저 쓰면 애매한 자투리가 남는" 구조면 그리디가 깨진다.

⏱️

실전 팁 — 반례를 빨리 만드는 3가지 시드:

① 경계값(0, 1, 최대치)을 섞은 작은 입력. ② "큰 걸 먼저"가 손해 보는 케이스. ③ "같은 점수인데 미래가 다른" 두 선택지. 이 세 가지로 안 깨지면 그리디 가설을 믿고 일단 제출해 봐도 된다.

기술 2 — 교환 논법 (Exchange Argument)

반례가 안 나오면, 이번엔 "왜 그리디가 항상 옳은가"를 짧게 논증해 본다. 그리디를 증명하는 정석 기법이다.

  1. 최적해 OPT가 있다고 가정한다. 단, OPT가 그리디와 다른 선택을 한 첫 지점이 있다고 하자.
  2. 그 지점에서 OPT의 선택을 그리디의 선택으로 바꿔치기(swap)해도 답이 나빠지지 않음을 보인다.
  3. 바꿔치기를 반복하면 OPT를 그리디 해로 바꿀 수 있다 → 그리디도 최적이다. 증명 끝.

예를 들어 회의실 배정(가장 빨리 끝나는 회의 먼저)이나 구명보트(가장 무거운 사람 + 가장 가벼운 사람) 같은 게 그렇다. "내 선택으로 바꿔도 손해가 없다"가 직관적으로 보이면 그리디는 거의 맞다.

📌

정리: 검증 순서 — ① 그리디 가설을 세운다 → ② 30초 반례 사냥 → ③ 반례 없으면 교환 논법으로 "swap해도 손해 없음"이 보이는지 확인 → ④ 둘 다 통과하면 그리디, 하나라도 막히면 DP.

다시 강조하지만 — 모든 테스트 케이스를 보는 게 아니라, 단 하나의 반례를 찾거나 못 찾는 것으로 판단한다.

04. 입력 크기(제약)로 후보 좁히기

문제의 "제한사항"에 적힌 N의 최대치는 출제자가 흘려주는 가장 큰 힌트다. 허용 시간복잡도를 역산하면 알고리즘 후보가 좁혀진다 (대략 1초 ≈ 1억 연산 기준).

N의 최대치허용 복잡도유력 후보
~ 1,000,000+O(N), O(N log N)그리디 · 정렬 · 투포인터 · 누적합
~ 100,000O(N log N)그리디 · 정렬 · 힙 · 1차원 DP
~ 5,000O(N²)2차원 DP · 완전탐색 일부
~ 500O(N³)구간 DP · 플로이드워셜
~ 20O(2ᴺ), O(N!)비트마스크 DP · 백트래킹 · 완전탐색
🧭

제약으로 읽는 실전 신호:

① N이 수십만~백만인데 최적해를 요구 → DP 배열이 너무 커지거나 O(N²)이 안 되니까 그리디일 확률↑.
② N이 작은데(수백~수천) "모든 경우" 냄새 → 상태 테이블을 만들 여유가 있으니 DP·완전탐색.
③ "경우의 수를 1,000,000,007로 나눈 나머지" → 거의 항상 DP 또는 조합 (그리디 아님).

물론 제약만으로 확정할 순 없다. 제약으로 후보를 좁히고 (섹션 04) → 문구 신호로 가설을 세우고 (섹션 06·07) → 반례·교환으로 검증 (섹션 03)하는 3단 콤보로 쓴다.

05. 문제를 읽을 때 판단 순서

플로우차트를 한 단계 더 다듬은 버전이다. "현재 최선이 전체 최선인가?"라는 막연한 질문 대신, 검증 가능한 질문으로 바꿨다.

1
최적해(최대·최소·최선)를 구하는가?
NO구현 / 시뮬레이션 / 완전탐색으로 간다
2
입력 크기 N을 본다 (섹션 04)
백만 단위 → 그리디 의심 / 수백~수천 → DP 의심
3
지금 고른 선택이 미래의 선택지를 막는가?
YES막는다 → DP 쪽으로 강하게 기운다 (4번 건너뛰고 6번)
4
그리디 가설을 세우고 30초 반례 사냥
반례 없음 + 교환논법 OK → Greedy 확정
5
반례가 나오거나 같은 상태가 반복 등장하는가?
YES → 상태와 점화식을 정의 → DP
6
DP 상태 공간이 너무 큰가?
YES → 그리디 재검토 / 차원 축소 / 다른 기법(BFS·이분탐색 등)
🎯

3번 질문이 핵심이다. "현재 최선이 전체 최선인가?"는 너무 추상적이라 판단이 안 된다. 대신 "지금 선택이 미래 선택지를 막는가?"로 바꾸면 구체적으로 답할 수 있다. 도둑질(인접 집 못 텀)·0/1 배낭(넣으면 용량 줄어듦)처럼 선택이 미래를 제약하면 거의 DP다.

06. 그리디를 암시하는 문제 문구

문제 텍스트에서 아래 신호가 보이면 그리디 가설을 먼저 세운다. (근데 가설일 뿐이다 — 반드시 섹션 03으로 검증해야 한다.)

신호 / 문구왜 그리디 냄새인가
"가능한 한 많이 / 적게", "최대한 ~"매 단계 극단적 선택을 반복하면 된다 — 정렬 후 끝에서부터
"끝나는 시간 / 마감이 빠른 순서로"구간 스케줄링의 전형 — 빨리 끝내고 다음을 받는 그리디
짝짓기·매칭 ("두 명씩 태운다")가장 큰 것 + 가장 작은 것을 묶는 투포인터 그리디
"더 이상 줄일 수 없을 때까지 제거"단조 스택(monotonic stack) 그리디
각 단계 선택이 서로 독립 (앞이 뒤의 가능 여부를 안 막음)탐욕적 선택 속성 성립 — 한 갈래만 봐도 됨
거스름돈인데 화폐 단위가 배수 관계 (500·100·50·10)큰 단위부터 쓰면 최적 — 배수 구조라 자투리 손해가 없음
🚧

함정 주의: "최대/최소를 구하라"는 문구 자체는 그리디 신호가 아니다. DP도 똑같이 최대/최소를 구한다. 갈리는 건 "한 선택이 미래를 막는가" 이거 하나뿐이다.

07. DP를 암시하는 문제 문구

아래 신호가 보이면 DP 가설을 먼저 세운다.

신호 / 문구왜 DP 냄새인가
"경우의 수를 구하라", "방법의 수" (+ mod 1e9+7)모든 경로를 세야 함 — 부분 경우의 수를 누적
"이것을 고르면 인접/다음 것은 못 고른다"선택이 미래를 제약 → 다 따져보고 최적 저장 (도둑질·스티커)
격자에서 "경로의 최소 비용 / 경로의 수"한 칸에 여러 경로가 모임 → 칸마다 최적 저장 (정수 삼각형·등굣길)
"N번째 값", "f(n) = f(n-1) + ..." 냄새점화식으로 정의되는 수열 (피보나치류)
"~로 표현할 수 있는가 / 만들 수 있는 최소 횟수"작은 부분 조합을 쌓아 큰 것을 구성 (N으로 표현·동전)
"연속 부분 수열 / 부분 집합"의 최적각 위치까지의 최적을 기억 (최대 부분합·LIS)
0/1 배낭 ("담거나 안 담거나, 용량 제한")담으면 용량이 줄어 미래가 바뀜 → 2차원 DP
🔥

가장 강한 DP 신호: "같은 부분 문제가 여러 경로에서 반복 등장" + "한 선택이 미래 선택지를 제약". 이 둘이 동시에 보이면 거의 확정 DP다.

08. 그리디인지 DP인지 구분하는 체크리스트

문제를 읽고 아래를 빠르게 체크해보자. G가 많으면 그리디, D가 많으면 DP 가설.

기운다질문
G한 번 고른 선택을 번복할 일이 없는가?
G정렬 한 번 + 순차 선택으로 끝날 것 같은가?
G각 단계 선택이 서로 독립적인가? (앞이 뒤의 가능 여부를 안 막음)
G30초 반례 사냥에서 반례가 안 나오고 교환논법이 직관적인가?
GN이 매우 커서(10⁵~10⁶) DP 배열·O(N²)이 부담스러운가?
D한 선택이 나중 선택의 가능 여부를 막는가?
D같은 부분 문제가 여러 경로에서 반복 등장하는가?
D"이걸 골랐다가 나중에 후회할 수도" 싶은가?
D반례가 떠오르는가? (큰 것부터 골랐더니 손해 보는 케이스)
D"경우의 수" / mod 연산 / 격자 경로 / 점화식 냄새가 나는가?

09. 그리디 대표 문제 분석

프로그래머스 고득점 Kit 「탐욕법(Greedy)」 대표 문제다. 문제는 직접 풀어보길 권하고, 여기선 "왜 그리디인지"를 텍스트 신호 중심으로 보자.

구명보트 Greedy
프로그래머스 · 고득점 Kit 탐욕법 (Lv.2)
문제 요약
사람마다 몸무게가 있고, 보트 하나에는 최대 2명까지·무게 합이 한계 이하여야 한다. 모두를 옮기는 데 필요한 최소 보트 수를 구한다.
그리디 신호
"최소 개수" + "두 명씩 짝짓기" → 가장 무거운 사람 + 가장 가벼운 사람을 묶는 매칭 신호.
판단
정렬 후 양끝 투포인터 그리디. 가장 무거운 사람을 가장 가벼운 사람과 태워보고, 안 되면 혼자 태운다. 교환 논법으로 최적임이 증명된다 (무거운 사람은 누군가와 묶여야 하는데, 가장 가벼운 사람과 못 묶이면 누구와도 못 묶인다).
반례 사냥
"가장 무거운 사람을 다른 사람과 묶으면 더 이득?" → 아니다. 가벼운 사람을 남겨도 그는 결국 누군가와 태워야 하니까 손해가 없다. 반례 없음 → 그리디.

Java · 구명보트 (그리디 + 투포인터)

import java.util.Arrays;

class Solution {
    public int solution(int[] people, int limit) {
        Arrays.sort(people);          // 오름차순 정렬: 양끝에서 가벼움/무거움을 잡기 위함
        int light = 0;                // 가장 가벼운 사람을 가리키는 포인터(왼쪽)
        int heavy = people.length - 1; // 가장 무거운 사람을 가리키는 포인터(오른쪽)
        int boats = 0;                // 사용한 보트 수(정답)

        while (light <= heavy) {      // 두 포인터가 교차할 때까지
            // 가장 무거운 사람과 가장 가벼운 사람을 함께 태울 수 있으면 둘 다 태운다
            if (people[light] + people[heavy] <= limit) {
                light++;              // 가벼운 사람도 탑승 → 포인터 전진
            }
            heavy--;                  // 무거운 사람은 어떤 경우든 이번 보트에 탑승
            boats++;                  // 보트 한 척 사용
        }
        return boats;
    }
}
큰 수 만들기 Greedy
프로그래머스 · 고득점 Kit 탐욕법 (Lv.2)
문제 요약
숫자 문자열에서 k개의 숫자를 제거해 만들 수 있는 가장 큰 수를 구한다.
그리디 신호
"가장 큰 수" + "제거" → 앞자리가 클수록 무조건 이득이라는 자릿값 구조. 앞에서부터 보면서 "뒤에 더 큰 숫자가 오면 앞의 작은 숫자를 버린다".
판단
단조 감소 스택 그리디. 스택의 top이 현재 숫자보다 작고 아직 제거 횟수가 남았으면 pop. 앞자리 우선이라는 자릿값 성질이 탐욕적 선택을 보장한다.
반례 사냥
"지금 작은 걸 안 버리고 남겨두면 이득?" → 자릿수가 같다면 앞자리가 큰 쪽이 항상 큰 수니까 손해. 반례 없음 → 그리디.

Java · 큰 수 만들기 (그리디 + 단조 스택)

import java.util.Deque;
import java.util.ArrayDeque;

class Solution {
    public String solution(String number, int k) {
        Deque<Character> stack = new ArrayDeque<>(); // 결과 자릿수를 쌓을 스택

        for (char c : number.toCharArray()) {
            // 제거 횟수(k)가 남아 있고, 스택 top이 지금 숫자보다 작으면
            // 앞의 작은 숫자를 버리는 게 더 큰 수를 만든다 → pop
            while (k > 0 && !stack.isEmpty() && stack.peek() < c) {
                stack.pop();
                k--;                  // 제거 1회 소모
            }
            stack.push(c);            // 현재 숫자는 일단 스택에 넣는다
        }
        // 끝까지 갔는데 제거 횟수가 남았다면(예: 단조 증가 문자열) 뒤에서 k개 제거
        while (k-- > 0) stack.pop();

        // 스택은 위가 마지막 자리니까, 아래(가장 앞자리)부터 문자열로 복원
        StringBuilder sb = new StringBuilder();
        stack.descendingIterator().forEachRemaining(sb::append);
        return sb.toString();
    }
}
체육복 Greedy
프로그래머스 · 고득점 Kit 탐욕법 (Lv.1)
문제 요약
체육복을 잃어버린 학생이 있고, 여벌을 가진 학생은 바로 앞/뒤 번호에게만 빌려줄 수 있다. 체육 수업을 들을 수 있는 최대 인원을 구한다.
그리디 신호
"인접한 번호끼리만 영향" + "최대 인원" → 앞에서부터 차례로 처리해도 손해가 없는 국소적 선택 구조.
판단
앞 번호부터 빌려주는 그리디. 여벌 가진 학생은 앞 번호(작은 번호)에게 먼저 빌려준다. 그래야 뒷사람이 받을 기회를 안 막는다 (교환 논법).
반례 사냥
"뒷사람한테 먼저 빌려주면?" → 뒷사람은 그다음 사람에게도 받을 수 있어서 손해 가능. 앞 우선이 항상 안전. 반례 없음 → 그리디.
📚

그리디 보너스 문제 (직접 풀어볼 것)

단속카메라 — 구간들을 모두 감시하는 최소 카메라 수. "끝나는 좌표가 빠른 순" 정렬 후 그리디 (회의실 배정과 동형). 조이스틱 — 상하 이동은 글자별 그리디, 좌우 이동은 최소 경로 비교. 둘 다 "끝/극단부터 처리" 신호.

10. DP 대표 문제 분석

프로그래머스 고득점 Kit 「동적계획법(DP)」 대표 문제. "왜 그리디로는 안 되고 DP인지"를 신호 중심으로 보자.

정수 삼각형 DP
프로그래머스 · 고득점 Kit DP (Lv.3)
문제 요약
숫자 삼각형의 꼭대기에서 바닥까지 대각선으로 한 칸씩 내려오며 거친 숫자의 합이 최대가 되는 경로를 찾는다.
DP 신호
"격자/삼각형 경로의 최댓값" + "한 칸에 도달하는 경로가 여러 개" → 각 칸까지의 최적합을 저장해야 함.
왜 그리디 ✗
"매 칸에서 더 큰 쪽으로 내려가기"(그리디)는 실패한다. 지금 작은 숫자를 밟아도 그 아래에 거대한 숫자가 있을 수 있으니까 — 지금 선택이 미래를 잘못 막는다.
상태/점화식
dp[i][j] = i행 j열까지의 최대 합 = triangle[i][j] + max(dp[i-1][j-1], dp[i-1][j]). 정답은 마지막 행의 최댓값.

Java · 정수 삼각형 (DP)

class Solution {
    public int solution(int[][] triangle) {
        int n = triangle.length;
        // dp[i][j] = (i,j)칸까지 내려오며 만들 수 있는 합의 최댓값
        int[][] dp = new int[n][n];
        dp[0][0] = triangle[0][0]; // 꼭대기는 그 칸 값 그대로

        for (int i = 1; i < n; i++) {
            for (int j = 0; j <= i; j++) {
                // 위에서 내려오는 두 경로(왼쪽 위 j-1, 오른쪽 위 j) 중 큰 값을 택한다
                int fromLeft  = (j > 0) ? dp[i-1][j-1] : 0; // 왼쪽 끝이면 왼쪽위 경로 없음
                int fromRight = (j < i) ? dp[i-1][j]   : 0; // 오른쪽 끝이면 오른쪽위 경로 없음
                dp[i][j] = triangle[i][j] + Math.max(fromLeft, fromRight);
            }
        }
        // 바닥 행에서 가장 큰 값이 전체 최대 경로 합
        int answer = 0;
        for (int j = 0; j < n; j++) answer = Math.max(answer, dp[n-1][j]);
        return answer;
    }
}
도둑질 DP
프로그래머스 · 고득점 Kit DP (Lv.4)
문제 요약
원형으로 늘어선 집들에서 돈을 턴다. 단, 인접한 두 집을 동시에 털 수 없다. 훔칠 수 있는 최대 금액을 구한다 (원형이라 첫 집과 마지막 집도 인접).
DP 신호
"이 집을 털면 옆집은 못 턴다" → 한 선택이 미래 선택지를 제약하는 전형적 신호. (섹션 05의 3번 질문에 YES)
왜 그리디 ✗
"금액 큰 집부터 털기"(그리디)는 실패. 예: [2, 3, 2] → 그리디는 가운데 3을 털고 끝이지만, 최적은 양끝 2+2=4. 큰 것부터가 미래를 잘못 막는 반례 존재.
상태/점화식
dp[i] = max(dp[i-1], dp[i-2] + money[i]) — i집을 안 털거나(앞 결과 유지), 털고 두 칸 전 결과를 더하거나. 원형이라 "첫 집 포함" / "마지막 집 포함" 두 경우로 나눠 각각 풀고 더 큰 값을 택한다.

Java · 도둑질 (원형 House Robber DP)

class Solution {
    public int solution(int[] money) {
        int n = money.length;
        // 원형: 첫 집과 마지막 집은 동시에 못 턴다.
        // 경우 1) 첫 집 포함 → 마지막 집 제외: 인덱스 [0 .. n-2]
        // 경우 2) 첫 집 제외 → 마지막 집 가능: 인덱스 [1 .. n-1]
        int case1 = robLine(money, 0, n - 2);
        int case2 = robLine(money, 1, n - 1);
        return Math.max(case1, case2);
    }

    // [start, end] 구간을 일직선으로 보고 인접 금지 최대합을 구한다
    private int robLine(int[] money, int start, int end) {
        int prev2 = 0;  // dp[i-2]: 두 칸 전까지의 최적
        int prev1 = 0;  // dp[i-1]: 한 칸 전까지의 최적
        for (int i = start; i <= end; i++) {
            // i집을 털지(prev2+money) / 안 털지(prev1) 중 큰 쪽
            int cur = Math.max(prev1, prev2 + money[i]);
            prev2 = prev1;   // 한 칸씩 앞으로 밀기
            prev1 = cur;
        }
        return prev1; // 구간 끝까지의 최적
    }
}
N으로 표현 DP
프로그래머스 · 고득점 Kit DP (Lv.3)
문제 요약
숫자 N을 사칙연산으로 이어붙여(예: N, NN, N+N…) 목표 수 number를 만들 때, N을 사용하는 최소 횟수를 구한다 (8회 초과면 -1).
DP 신호
"~로 표현할 수 있는가" + "최소 횟수" + "작은 부분 조합을 결합" → k개 사용해 만들 수 있는 수들의 집합을 쌓아 올리는 구조.
왜 그리디 ✗
"매번 가장 큰 수부터" 같은 국소 규칙으론 number를 못 만든다. i개와 k-i개의 결과를 모든 방식으로 조합해야 하니까 부분 문제를 모두 저장하는 DP가 필요하다.
상태/점화식
dp[k] = N을 k개 써서 만들 수 있는 수들의 집합. dp[k]는 dp[i]와 dp[k-i](i=1..k-1)의 원소들을 +−×÷ 한 결과 ∪ "N을 k번 이어붙인 수".
📚

DP 보너스 문제 (직접 풀어볼 것)

등굣길 — 격자에서 물웅덩이를 피해 집→학교 최단경로의 경우의 수(+ mod). dp[i][j] = dp[i-1][j] + dp[i][j-1]. "경로의 수 + mod" = 강한 DP 신호. 사칙연산 — 식의 괄호 묶는 방식에 따른 최대/최소, 구간 DP dp[i][j].

11. 그리디로 착각하기 쉬운 DP 문제

"국소적으로 좋아 보이는 선택"이 함정인 경우들이다. 공통점은 지금 선택이 미래를 제약한다는 거다.

①

거스름돈 — 임의 단위

"동전 개수 최소" → 큰 단위부터 쓰면 될 것 같다(그리디). 근데 단위가 {1, 4, 5}이고 8원이면 그리디는 5+1+1+1(4개), 최적은 4+4(2개). 배수 관계가 아닌 단위면 그리디 ✗ → DP. (단위가 500·100·50·10처럼 배수면 그리디 OK)

②

0/1 배낭 (Knapsack)

"단위 무게당 가치가 높은 것부터 담기"(그리디)는 물건을 쪼갤 수 있을 때(분할 배낭)만 최적이다. 쪼갤 수 없는 0/1 배낭에선 실패 — 담으면 용량이 줄어 미래 선택이 바뀌니까 dp[i][w] 2차원 DP가 필요하다.

③

도둑질 / 최대 부분합

"큰 것부터 욕심내기"가 인접 제약 때문에 깨진다 (섹션 10 도둑질의 [2,3,2] 반례). 연속 부분합 최대(카데인)도 "양수만 더하기" 같은 그리디로는 음수를 건너뛰는 최적 구간을 놓친다 → dp[i]=max(nums[i], dp[i-1]+nums[i]).

🧯

공통 탈출 신호: 이 셋 모두 "지금 고른 선택이 미래의 자원(용량·인접·연속성)을 소모/제약한다". 이 냄새가 나면 그리디 가설을 의심하고 반례부터 만들어 보자.

12. DP로 착각하기 쉬운 그리디 문제

"최대/최소를 구하라"는 말에 겁먹고 DP 테이블을 짜기 시작하는 경우들. 사실은 정렬 한 번 + 그리디로 끝난다.

①

회의실 배정 / 단속카메라

"최대 회의 수 / 최소 카메라 수" → 최적화라서 DP처럼 보인다. 근데 "끝나는 시간이 빠른 순"으로 정렬해 그리디로 고르면 최적이다 (교환 논법으로 증명됨). DP로 풀면 오히려 느리고 복잡하다.

②

분할 가능 배낭 (Fractional Knapsack)

0/1 배낭과 한 글자 차이지만, 물건을 쪼갤 수 있으면 "단위 가치 높은 것부터 채우기" 그리디가 정확히 최적. 쪼갤 수 있다는 한 조건이 DP를 그리디로 바꾼다.

③

큰 수 만들기 / 구명보트

둘 다 "가장 큰/최소"를 요구하는 최적화지만(섹션 09), 자릿값·매칭이라는 구조 덕에 그리디가 정답. "최적화 = DP"라는 반사부터 버리자.

🧭

공통 신호: "정렬 기준 하나만 잘 잡으면 순서대로 고르는 것으로 끝"이면 그리디다. DP 상태를 정의하려 해도 "기억해둘 게 없다"면 그것도 그리디 신호.

시험장에서 문제를 받았을 때 머릿속으로 돌릴 최종 체크 순서다. 앞 섹션들의 압축판.

한 문장으로 외울 결론: 그리디인지 DP인지는 "케이스를 다 봐서"가 아니라 "단 하나의 반례를 찾으려 시도해서" 판단한다. 반례가 나오거나 지금 선택이 미래를 막으면 DP, 아무리 깨려 해도 안 깨지고 교환해도 손해가 없으면 Greedy.

🛟

막히면 — 안전한 디폴트: 시험장에서 끝까지 확신이 안 서면 — 제약이 작으면(N≤수천) DP/완전탐색으로 정확도부터 확보하고, 제약이 크면 그리디 가설을 세워 반례 1개만 더 찾아본 뒤 제출한다. 그리디는 틀리면 크게 틀리니까, 의심되면 DP가 안전하다.
