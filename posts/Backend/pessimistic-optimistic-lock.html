비관적 락 & 낙관적 락

동시 수정 문제와 비관적 락·낙관적 락의 차이, SQL·JPA에서의 적용을 정리합니다.

ConcurrencyJPADatabase

1️⃣ 문제 : 동시성

여러 요청이 같은 데이터를 동시에 수정하면 문제가 생김

  • 예시 (지갑)
현재 잔액 = 10000

동시에 결제 요청

A → 7000 결제
B → 5000 결제

그 결과

A update → 3000
B update → 5000

최종 결과

balance = 5000

2️⃣ 해결 방법 = Lock

이 문제를 해결하는 방법이 Lock(잠금)이다.

대표적으로 두 가지가 있다.

비관적 락 (Pessimistic Lock)
낙관적 락 (Optimistic Lock)

3️⃣ 비관적 락 (Pessimistic Lock)

충돌이 발생할 가능성이 높다고 가정하고 처음부터 DB에 Lock을 걸어버리는 방식

→ 내가 쓰는 동안 다른 사람 접근 금지

동작 방식

  • 예시 
    Thread A → 지갑 조회 + LOCK
Thread B → 지갑 조회 시도

    DB 상태

    A → 사용 중
B → 대기
    • A가 끝나야 B가 실행된다.

실제 SQL

SELECT *
FROM wallets
WHERE id = 1
FOR UPDATE
  • FOR UPDATE가 row lock을 건다

JPA 사용 방법

@Lock(LockModeType.PESSIMISTIC_WRITE)
Wallet findById(Long id);

✅ 특징

  • 장점
    • 데이터 충돌 절대 발생 안함
  • 단점
    • 대기 발생
    • 성능 저하
    • DeadLock 가능

4️⃣ 낙관적 락 (Optimistic Lock)

충돌이 거의 없다고 가정하여 일단 실행하고, 충돌 발생 시 롤백하는 방식

동작 방식

  • 지갑 상태 
    balance = 10000
version = 1
  • Thread A 
    update wallet
set balance = 3000
where id = 1
and version = 1
    • 성공 
      version = 2
  • Thread B 
    update wallet
where version = 1
    • 하지만 실제 DB 
      version = 2
    • 그래서 
      update 0 rows
    • JPA는 OptimisticLockException 을 발생시킨다.
