JaCoCo 코드 커버리지

JaCoCo의 바이트코드 계측 원리와 Line/Branch 등 커버리지 지표, Gradle 설정과 jacocoTestCoverageVerification으로 최소 기준을 강제하는 방법을 정리합니다.

TestingJaCoCoGradleCoverage

JaCoCo란

JaCoCo(Java Code Coverage)는 테스트가 실제 코드를 얼마나 실행했는지 측정하는 코드 커버리지 도구다. 바이트코드에 프로브(probe)를 심어 클래스가 로드·실행되는 시점을 계측(instrumentation)하는 방식으로 동작하며, 소스 컴파일 결과물을 건드리지 않고도 실행 경로를 추적할 수 있다.

커버리지 지표

  • Instructions (C0) — 바이트코드 명령어 단위 실행 여부. 가장 세밀한 지표
  • Branches (C1) — if, switch 등 분기 중 실제로 탄 경로의 비율
  • Line — 실행된 소스 라인 비율. 가장 직관적으로 보는 지표
  • Complexity — 순환 복잡도(Cyclomatic Complexity) 기준으로 커버된 경로 비율
  • Method / Class — 최소 1개 이상의 인스트럭션이 실행된 메서드·클래스 비율

실무에서는 대개 Line과 Branch 커버리지를 기준으로 목표치를 관리한다. Line만 보면 분기 하나가 누락돼도 100%로 보일 수 있어서, 조건문이 많은 코드는 Branch 커버리지를 함께 봐야 한다.

Gradle 설정

plugins {
    id 'jacoco'
}

jacoco {
    toolVersion = '0.8.11'
}

test {
    finalizedBy jacocoTestReport // test 실행 후 리포트 자동 생성
}

jacocoTestReport {
    dependsOn test
    reports {
        html.required = true
        xml.required = true // SonarQube 등 외부 연동 시 필요
    }
}
./gradlew test jacocoTestReport
# 결과: build/reports/jacoco/test/html/index.html

커버리지 최소 기준 강제 (jacocoTestCoverageVerification)

빌드 시점에 커버리지가 기준치 미만이면 빌드를 실패시켜, 커버리지 하락을 CI 단계에서 막을 수 있다.

jacocoTestCoverageVerification {
    violationRules {
        rule {
            limit {
                counter = 'LINE'
                minimum = 0.80
            }
            limit {
                counter = 'BRANCH'
                minimum = 0.70
            }
        }

        rule {
            element = 'CLASS'
            excludes = ['**.*Application', '**.*Config', '**.dto.*']
            limit {
                counter = 'LINE'
                minimum = 0.80
            }
        }
    }
}

check.dependsOn jacocoTestCoverageVerification

측정 대상 제외

DTO, Config, Application 진입점처럼 비즈니스 로직이 없는 클래스는 커버리지 지표를 왜곡하므로 제외하는 것이 일반적이다.

jacocoTestReport {
    afterEvaluate {
        classDirectories.setFrom(
            files(classDirectories.files.collect {
                fileTree(dir: it, excludes: [
                    '**/*Application*',
                    '**/dto/**',
                    '**/config/**'
                ])
            })
        )
    }
}

동작 원리 — 왜 바이트코드 계측인가

  • 소스코드가 아닌 클래스 파일 로딩 시점에 On-the-fly로 프로브를 주입한다 (Java Agent 방식)
  • 각 프로브는 boolean 배열의 특정 인덱스를 true로 표시하는 역할만 하므로 런타임 오버헤드가 작다
  • 테스트 실행이 끝나면 JVM 종료 시점 또는 dump() 호출 시점에 프로브 데이터를 .exec 파일로 직렬화한다
  • 리포트 생성 단계에서 .exec 파일과 원본 클래스 파일(디버그 심볼 포함)을 대조해 라인/분기 단위로 매핑한다

이 방식 때문에 컴파일 시 디버그 정보(-g, 라인 넘버 테이블)가 없으면 라인 단위 매핑이 부정확해질 수 있다.

흔한 함정

  • Lombok @Data, @Builder 생성 코드가 커버리지 분모에 포함되어 수치가 낮아 보이는 경우 → lombok.config에 lombok.addLombokGeneratedAnnotation = true를 추가하면 JaCoCo가 자동으로 제외한다
  • 테스트가 있어도 assert가 없는 경우 — 실행만 되고 검증은 안 되므로 커버리지는 높아도 버그를 못 잡는다. 커버리지는 "실행됨"을 보장할 뿐 "검증됨"을 보장하지 않는다
  • 100% 커버리지를 맹목적 목표로 삼는 것 — getter/setter, 단순 위임 코드까지 억지로 테스트를 채우면 유지보수 비용만 늘어난다. 비즈니스 로직·분기 위주로 목표를 잡는 편이 낫다
