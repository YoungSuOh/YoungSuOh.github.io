GitHub Actions로 테스트 CI 자동화

GitHub Actions로 PR마다 테스트를 자동 실행하고, 테스트 리포트·커버리지 검증을 붙여 브랜치 보호와 연결하는 CI 워크플로 구성을 정리합니다.

TestingCI/CDGitHub ActionsDevOps

왜 CI에서 테스트를 자동화하는가

로컬에서만 테스트를 돌리면 "내 컴퓨터에서는 됐는데" 문제를 피할 수 없다. PR이 올라올 때마다 동일한 환경에서 전체 테스트 스위트를 실행해 회귀를 조기에 잡고, 리뷰어가 커버리지·빌드 결과를 신뢰하고 머지 여부를 판단할 수 있게 하는 것이 CI의 역할이다. GitHub Actions는 저장소에 .github/workflows/*.yml 파일만 추가하면 별도 서버 없이 이를 구성할 수 있다.

기본 워크플로 — PR마다 테스트 실행

name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: 'gradle' # ~/.gradle/caches 캐싱 → 빌드 시간 단축

      - name: Run tests
        run: ./gradlew test

on.pull_request과 on.push를 함께 두면 PR 단계와 main 머지 시점 양쪽에서 검증된다. cache: 'gradle'은 의존성·빌드 캐시를 저장해 매 실행마다 전체 다운로드를 반복하지 않게 한다.

테스트 결과 리포트 남기기

테스트가 실패했을 때 어떤 케이스가 깨졌는지 Actions 로그를 뒤지지 않고 PR 화면에서 바로 보려면 결과를 아티팩트나 체크로 남긴다.

      - name: Run tests
        run: ./gradlew test

      - name: Publish test report
        if: always() # 테스트가 실패해도 리포트는 업로드
        uses: dorny/test-reporter@v1
        with:
          name: JUnit Results
          path: '**/build/test-results/test/*.xml'
          reporter: java-junit

if: always()가 없으면 이전 스텝(테스트)이 실패했을 때 리포트 업로드 스텝 자체가 스킵돼, 정작 실패 원인을 확인할 수 없게 된다.

커버리지 기준 강제

JaCoCo의 jacocoTestCoverageVerification을 CI 스텝으로 실행하면 커버리지가 기준선 아래로 떨어지는 PR을 빌드 실패로 자동 차단할 수 있다.

      - name: Verify coverage
        run: ./gradlew jacocoTestReport jacocoTestCoverageVerification

      - name: Upload coverage report
        uses: actions/upload-artifact@v4
        with:
          name: jacoco-report
          path: build/reports/jacoco/test/html

브랜치 보호와 연결

워크플로가 초록불이어도 강제하지 않으면 무시하고 머지할 수 있다. 저장소 Settings → Branches → Branch protection rule에서 main에 대해 Require status checks to pass before merging을 켜고 CI 워크플로의 job 이름(예: test)을 필수 체크로 지정해야, 테스트가 실패한 PR은 물리적으로 머지 버튼이 막힌다.

실행 시간 최적화

  • 의존성 캐싱 — setup-java의 cache: 'gradle' 또는 actions/cache로 ~/.gradle, node_modules 등을 캐싱
  • 매트릭스 대신 필요한 조합만 — 여러 JDK/OS 조합을 strategy.matrix로 다 돌리면 비례해서 느려지므로, 실제로 지원해야 하는 조합만 남긴다
  • 테스트 분할(sharding) — 테스트가 많아지면 --tests 필터나 병렬 job으로 스위트를 나눠 wall-clock 시간을 줄인다
  • 불필요한 트리거 제거 — 문서(*.md)만 변경된 커밋까지 전체 테스트를 돌릴 필요는 없으므로 paths-ignore로 제외한다

흔한 함정

  • 로컬과 CI의 JDK/Gradle 버전 불일치 — 로컬은 통과하는데 CI만 실패하는 원인의 상당수가 버전 차이다. gradle-wrapper.properties로 Gradle 버전을 고정하고 setup-java 버전을 명시한다
  • Flaky 테스트를 재실행으로만 덮는 것 — retry 액션으로 실패를 감추면 근본 원인(테스트 간 상태 공유, 타이밍 의존)이 누적된다. 재시도는 임시방편이고 원인 제거가 우선이다
  • 시크릿을 워크플로 로그에 그대로 출력 — run: echo ${{ secrets.DB_PASSWORD }} 같은 디버그 로그는 마스킹되긴 하지만, 문자열 조합·인코딩으로 우회 노출될 수 있어 애초에 로그에 찍지 않는다
