[GC] GC의 발전 흐름

Stop-The-World 시간을 줄이기 위한 Java GC의 진화 — Serial → Parallel → CMS → G1 → ZGC/Shenandoah까지 각 GC의 동작 방식과 트레이드오프, Concurrent 수행 비중의 확대 과정을 정리합니다.

GC 알고리즘의 발전 흐름

Java GC는 "멈춤(Stop-The-World) 시간을 어떻게 줄일 것인가"를 중심으로 진화했다.

힙 크기가 커지고 응답 지연이 중요해질수록, GC는 점점 더 많은 작업을 애플리케이션 스레드와 동시(concurrent)로 수행하는 방향으로 발전했다.

1. Serial GC

  1. 가장 단순한 GC.
  2. Young/Old 영역 모두 단일 스레드로 수집. 수집 중 모든 애플리케이션 스레드 정지(STW 발생).
  3. 용도 — 클라이언트 앱, 임베디드, 소규모 데몬.
  4. 옵션 — -XX:+UseSerialGC
  5. 단점 — 멀티코어 활용 불가, 힙이 커지면 STW 시간 폭증.

2. Parallel GC

  1. "멀티 코어를 활용해 STW를 짧게"
  2. Young/Old 수집(GC 작업)을 여러 스레드가 병렬로 수행. 단, 여전히 수집 중에는 STW.
  3. 목표 — 처리량(Throughput) 최대화 — 전체 실행 시간 중 GC 시간 비율을 줄이는 것.
  4. 용도 — 배치 처리, 응답성보다 처리량이 중요한 서버.
  5. 옵션 — -XX:+UseParallelGC (JDK 8 기본값)
  6. 단점 — 응답 지연(latency)에는 부적합. STW가 짧아졌을 뿐 여전히 존재.

3. CMS (Concurrent Mark Sweep)

  1. "GC 작업의 대부분을 애플리케이션과 동시에 수행"
  2. 동작 — Old 영역 수집을 4단계로 분리
    1. Initial Mark (STW) — GC Root 직접 참조 객체만 표시
    2. Concurrent Mark — 앱 실행과 동시에 객체 그래프 추적
    3. Remark (STW) — 동시 마킹 중 변경된 참조 재확인
    4. Concurrent Sweep — 앱 실행과 동시에 미사용 객체 회수
  3. 옵션 — -XX:+UseConcMarkSweepGC
  4. 장점 — STW가 Initial Mark / Remark 단계로 짧게 두 번만 발생 → 응답 지연 대폭 감소.
  5. 단점
    1. Compaction 없음 → 메모리 단편화 발생, 결국 Full GC(Serial Old) 트리거 시 큰 STW
    2. CPU 자원을 GC가 지속 소비 → 처리량 손실
    3. "Concurrent Mode Failure" 발생 시 치명적

    👉 단편화 문제와 복잡성으로 JDK 9에서 deprecated, JDK 14에서 제거.

4. G1 GC (Garbage First)

  1. "힙을 작은 Region으로 쪼개 예측 가능한 GC" 
    [Region][Region][Region][Region]...
    • 각 Region은 상황에 따라 Eden, Survivor, Old의 역할을 가진다.
  2. 동작
    1. 힙을 고정 크기 Region (보통 1MB~32MB)으로 분할
    2. Young/Old/Humongous 역할이 Region 단위로 동적 할당
    3. 쓰레기가 많은 Region부터 우선 수집 ("Garbage First")
    4. Concurrent Marking + Evacuation (STW지만 병렬 + Region 단위라 짧음)
  3. 옵션 — -XX:+UseG1GC (JDK 9+ 기본값)
  4. 장점
    1. 사용자가 목표 STW 시간 지정 가능 (-XX:MaxGCPauseMillis) → 예측 가능성
    2. Compaction 수행 → CMS의 단편화 문제 해결
    3. 대용량 힙(수 GB~수십 GB)에서 안정적
  5. 단점
    1. 작은 힙·짧은 일생 객체 위주 워크로드에선 Parallel GC보다 처리량 낮을 수 있음
    2. Region 관리 오버헤드, Remembered Set 메모리 비용

5. ZGC & Shenandoah

  1. "수백 GB 힙에서도 STW를 ms 단위로"
    1. 두 GC 모두 거의 모든 작업을 concurrent로 수행하여 STW를 10ms 이하(현재는 1ms 이하)로 만드는 것이 목표.

1️⃣ ZGC (Oracle, JDK 11 experimental, JDK 15 production)

  • Colored Pointer — 64비트 포인터에 메타데이터 비트 포함 — 객체 상태를 포인터로 표현
  • Load Barrier — 객체 참조 시 GC 상태 확인 및 자동 재매핑
  • Concurrent Relocation — 객체 이동도 앱과 동시에 수행
  • JDK 21+ — Generational ZGC 등장 — 약한 세대 가설을 활용해 처리량까지 개선.
  • 옵션 — -XX:+UseZGC (-XX:+ZGenerational)

2️⃣ Shenandoah (Red Hat, JDK 12 experimental, JDK 15 production)

  • Brooks Pointer / Load Reference Barrier — 객체 헤더에 forwarding pointer
  • Concurrent Evacuation & Compaction — 마킹/이동/업데이트 전부 동시 수행
  • 특징 — ZGC와 유사한 목표. ZGC가 Colored Pointer로 64비트에 종속적인 반면, Shenandoah는 32비트도 일부 지원.
  • 옵션 — -XX:+UseShenandoahGC
