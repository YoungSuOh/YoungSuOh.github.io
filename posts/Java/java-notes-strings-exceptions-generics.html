Java 정리 ① — 문자열·예외·제네릭

String 리터럴 vs new String, StringBuilder·StringBuffer, Exception·Error, throw·throws, finally, Throwable, 제네릭까지 정리합니다.

JavaStringExceptionGenerics

시리즈 ① 문자열·예외·제네릭 · ② 람다·스트림·어노테이션 · ③ System.out 심화

Q1) String literal과 new String("")의 차이

둘 다 String 객체를 만들지만, 메모리 할당·재사용 방식이 다릅니다.

1) String 리터럴 ("Hello")

String s1 = "Hello";
String s2 = "Hello"; // 같은 리터럴
  • 리터럴은 힙의 String Constant Pool에 올라가고, 동일 문자열이 있으면 같은 인스턴스를 참조합니다.
  • s1, s2 같은 참조 변수는 스택에 있고, 풀 안의 객체를 가리킵니다.
  • 메모리 측면에서 유리한 경우가 많습니다.

2) new String("Hello")

String s3 = new String("Hello");
String s4 = new String("Hello"); // 별도 객체
  • 호출마다 힙에 새 String 객체가 생깁니다.
  • 리터럴이 풀에 함께 만들어질 수 있어(내부 char[] 공유 등 JDK 구현에 따름) 세부는 버전마다 다르지만, == 관점에서는 보통 서로 다른 객체입니다.

Q2) String, StringBuilder, StringBuffer

모두 문자열을 다루지만 불변/가변과 스레드 안전성에서 갈립니다.

String

  • 불변(Immutable) — 수정 시마다 새 객체가 생깁니다.
  • 리터럴은 풀을 활용해 재사용이 가능합니다.
String str1 = "Hello";
str1 = str1 + " World"; // 새 String — 반복 연결 시 비효율

StringBuilder

  • 가변, 내부 버퍼를 수정합니다.
  • 싱글 스레드에서 연결·수정이 많을 때 적합합니다.
StringBuilder sb = new StringBuilder("Hello");
sb.append(" World");
System.out.println(sb.toString());

StringBuffer

  • 가변은 동일하지만 메서드에 synchronized가 있어 스레드 안전합니다.
  • 락 비용 때문에 단일 스레드에서는 보통 StringBuilder가 더 빠릅니다.

정리 불변만 필요하면 String, 자주 바꾸면 StringBuilder, 멀티스레드 공유 버퍼면 StringBuffer를 고려합니다.

Q3) Exception과 Error

구분 Exception Error
설명 애플리케이션에서 다룰 수 있는 예외적 상황 JVM·시스템 수준의 심각한 문제
복구 잡아서 처리하는 것이 일반적 복구 기대하기 어렵고 catch 비권장
예 IOException, NullPointerException OutOfMemoryError, StackOverflowError

Checked vs Unchecked

  • Checked — 컴파일러가 처리(try/catch 또는 throws)를 요구. 예: IOException.
  • Unchecked — RuntimeException 계열. 선언 강제는 없지만 설계·검증은 필요합니다.

Q6) throw와 throws

  • throw — 코드에서 예외 인스턴스를 직접 던짐.
  • throws — 메서드 시그니처에 던질 수 있는 예외를 선언. 호출자가 처리하도록 넘깁니다. Checked는 특히 필요합니다.
void check(int n) throws IllegalArgumentException {
  if (n < 0) throw new IllegalArgumentException("음수");
}

Q7) finally의 역할

예외 발생 여부와 관계없이 거의 항상 실행되는 블록입니다. DB 연결·스트림 닫기 등 리소스 정리에 씁니다. (일부 JVM 종료·무한 대기 등은 제외)

Java 7+에서는 try-with-resources로 AutoCloseable 정리를 더 안전하게 쓰는 편이 좋습니다.

Q8) Throwable과 Exception

Throwable이 최상위이고, 그 아래 Error와 Exception이 있습니다. Exception은 복구·처리를 전제로 하고, Error는 시스템 한계에 가깝습니다.

catch (Throwable t)는 Error까지 삼켜 버릴 수 있어 일반 코드에서는 피하는 것이 좋습니다.

Q9) 제네릭이란, 왜 쓰나

클래스·메서드에서 타입을 파라미터로 두어, 컴파일 시점에 타입을 검사하고 캐스팅을 줄이는 기능입니다.

// 제네릭 전: Object 리스트 → 꺼낼 때 캐스팅, 런타임 ClassCastException 위험
// 제네릭 후:
List<String> list = new ArrayList<>();
list.add("Hello");
// list.add(123); // 컴파일 에러
String s = list.get(0);

Q10) 제네릭을 쓴 경험

프로젝트에서 공통 예외 응답을 맞추기 위해 커스텀 예외 + AOP(예: @ControllerAdvice 또는 Aspect)로 처리한 경험이 있습니다. 응답 DTO를 ApiResponse<T> 형태로 두면 본문 타입을 한 번에 묶어 줄 수 있고, 컴파일 타임에 일관된 형식을 유지하기 좋습니다.
