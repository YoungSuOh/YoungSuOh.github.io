Nginx

  • Nginx는 흔히 웹 서버나 리버스 프록시 서버로 사용되는 소프트웨어야. 웹 서버 역할을 할 때, 정적 파일 (HTML, CSS, JavaScript, 이미지 등)을 클라이언트(예: 웹 브라우저)에 제공하는 데 최적화된 서버다.

Nginx와 Vite의 차이

  • Vite 개발 서버는 주로 개발 중에 사용할 수 있도록 빠른 개발 환경과 핫 리로드(코드 수정 시 즉시 반영되는 기능) 같은 편리한 기능을 제공한다.
  • 반면 Nginx는 프로덕션 환경에서 정적 파일을 제공하기에 최적화되어 있어, 성능과 효율성이 뛰어나다.
  • Vite 프로젝트를 빌드하면 dist 폴더에 최적화된 정적 파일들이 생성되는데, 이 파일들을 Nginx가 서빙하는 방식으로 배포하게 되는 것이다.

톰캣과 Nginx의 차이

톰캣(Tomcat)

  • 톰캣은 주로 Java 기반의 웹 애플리케이션(예: Spring 애플리케이션)을 실행하기 위한 애플리케이션 서버야.
  • 동적 웹 콘텐츠(예: 데이터베이스에서 정보를 가져오는 웹페이지)를 처리하는 데 적합하지.
  • 보통 톰캣은 JSP 파일이나 서블릿 같은 Java 코드를 실행하고, 이 결과를 웹 브라우저에 전송해.

Nginx

  • Nginx는 주로 정적 파일(HTML, CSS, JavaScript, 이미지 등)을 빠르게 서빙하는 데 특화된 웹 서버야.
  • Vite로 빌드한 정적 리소스는 Java 코드 실행이 필요 없고, 단순한 파일 제공만으로 웹 페이지가 작동하기 때문에 Nginx가 적합해.
  • Nginx는 또한 리버스 프록시, 로드 밸런싱, 보안 기능을 지원해서, 클라이언트의 요청을 특정 서버로 라우팅하거나 부하를 분산할 수 있어.

Nginx를 사용하는 이유

  • Vite 프로젝트는 프론트엔드에서 주로 정적 파일을 생성해, 이 파일들만 잘 서빙하면 브라우저에서 웹 애플리케이션이 정상적으로 작동한다.
  • 따라 톰캣을 통해 Java 기반 애플리케이션을 실행할 필요 없이, Nginx로 정적 파일을 제공하면 더 효율적으로 애플리케이션을 배포할 수 있는 거다
  • 요약하자면, 톰캣은 서버사이드 Java 애플리케이션에 적합하고, Nginx는 Vite 같은 정적 파일 기반 프론트엔드 프로젝트를 서빙하는 데 적합하다.

Jenkins pipeline 구축과정

Jenkins Pipeline 구조

  1. 먼저 local 프로젝트에서 Dockerfile을 만들어 Node.js 빌드 환경 설정과 Nginx 배포 환경설정에 대한 내용을 담아서 Github에 Push를 진행한다.
  2. NCP 서버를 생성하여 Docker 엔진을 설치하고, 젠킨스 컨테이너를 생성한다.
  3. Jenkins에 접속하여 pipeline을 구축한다. 이때 pipeline 과정은 다음과 같이 진행하였다.
    1. Checkout 단계
      1. Jenkins는 GitHub에서 프로젝트 코드를 체크아웃 진행
      2. git_credentials 자격 증명을 사용하여 GitHub에 인증
      3. 코드가 지정된 브랜치(main)를 기준으로 가져
    2. Build Docker Image 단계
      1. Jenkins는 Docker를 사용하여 React 앱의 Docker 이미지를 빌드
      2. Dockerfile을 사용하여 이미지를 생성
      3. 이 과정에서 Node.js와 Nginx 이미지를 가져와 애플리케이션을 빌드하고, Nginx가 정적 파일을 서빙할 수 있도록 준비
    3. Push to Docker Hub 단계
      1. Jenkins는 Docker Hub에 로그인한 후 youngsuoh/springreact:26 이미지를 push
        1. ⭐ 이때 굳이 Docker Hub에 push하는 이유는 도커는 기존 이미지를 재활용하는 것이 가능하기 때문에, 매번 새로 만들면서 빌드하는 소요보다 훨씬 덜하기 때문이다.
    4. Deploy on NCP 단계
      1. Jenkins는 NCP 서버에 SSH를 통해 접속
      2. NCP 서버에서 Docker Hub에 저장된 이미지를 pull한다.
      3. 기존의 컨테이너를 중지 및 삭제한 후, 새로운 컨테이너(container-name)를 실행
      4. Nginx가 React 앱을 80번 포트에서 제공하며, Spring Boot API와 통신할 준비가 완료된다,
    5. 파이프라인 종료

Jenkins pipeline 구축 실습

1. 로컬환경에서 Dockerfile을 만들고 Github에 push

  • Dockerfile 
    # Node.js 20으로 업데이트
FROM node:20 AS build

# 경로 설정하기
WORKDIR /app

# package.json과 package-lock.json을 워킹 디렉토리에 복사
COPY package.json ./

# 의존성 설치
RUN npm install

# 모든 파일을 도커 컨테이너의 워킹 디렉토리에 복사
COPY . .

# 프로젝트 빌드
RUN npm run build

# 실제 배포용 이미지 설정
FROM nginx:alpine

# 빌드 결과물을 Nginx 디렉토리에 복사
COPY --from=build /app/dist /usr/share/nginx/html

# 80번 포트 노출
EXPOSE 80

# Nginx 실행
CMD ["nginx", "-g", "daemon off;"]
    • Node.js 빌드 환경 설정과 Nginx 배포 환경설정에 대한 내용을 담았다.
  • Gihub push

2. NCP 서버에 도커 엔진과 젠킨스를 설치하여 파이프 라인 구축 준비

sudo apt update
sudo apt install docker.io
  • Jenkins Docker 컨테이너 실행
docker run -d -p 8080:8080 -p 50000:50000 --name jenkins \
-v jenkins_home:/var/jenkins_home \
-v /var/run/docker.sock:/var/run/docker.sock \
jenkins/jenkins:lts
  • docker run -d: d 옵션은 Jenkins를 백그라운드에서 실행하도록 설정한다.
  • p 8080:8080: Jenkins 웹 인터페이스에 접근할 수 있도록 호스트의 8080번 포트를 컨테이너의 8080번 포트와 연결한다.
  • Jenkins의 기본 포트가 8080이므로, 웹 브라우저에서 8080 포트로 접속하면 Jenkins UI에 접근할 수 있습니다.
  • p 50000:50000: Jenkins의 에이전트와 서버 간 통신에 사용되는 포트를 개방한다.이 포트는 Jenkins 에이전트가 분산 빌드 서버로 연결할 때 필요하다.
  • v jenkins_home:/var/jenkins_home: v 옵션은 볼륨을 지정하여 Jenkins의 데이터를 호스트 시스템에 영구적으로 저장할 수 있도록 한다.
    • jenkins_home 볼륨을 /var/jenkins_home 디렉토리와 연결하여, Jenkins 설정 파일 및 작업 데이터를 컨테이너가 중지되거나 삭제되어도 유지할 수 있다.
    • 만약 젠킨스를 삭제해야 하는 상황이 벌어질 때, 기존 내용을 삭제해야 하므로 백업은 필수다.
  • ⭐v /var/run/docker.sock:/var/run/docker.sock: 이 옵션은 호스트의 Docker 소켓 파일(/var/run/docker.sock)을 Jenkins 컨테이너에 연결한다.
    • 이렇게 하면 Jenkins 컨테이너 내에서 Docker 명령을 실행할 수 있어, Jenkins가 다른 Docker 컨테이너를 생성하거나 관리할 수 있게 된다.
    • 젠킨스 내에서 자동화를 위하여 도커를 빌드해야 하기 때문에 꼭 필요한 옵션이다.
  • 이제 http://{공인 IP}:8080 으로 젠킨스가 접근이 가능해진다.
    • docker logs {container Id} 로 비밀번호를 확인해서 로그인 해주자.
  • Jenkins안에 Docker CLI 설치
    1. Jenkins 컨테이너에 root 사용자로 접속 
      docker exec -it -u root jenkins /bin/bash
    2. apt update 및 Docker CLI 설치 
      apt update
apt install -y docker.io
    3. Jenkins 컨테이너 내부에서 Docker 소켓에 접근 권한 부여 
      usermod -aG docker jenkins
ls -l /var/run/docker.sock
// 결과 srw-rw---- 1 root docker ... /var/run/docker.sock
sudo chmod 666 /var/run/docker.sock
// 모든 사용자에게 Docker 소켓에 접근할 수 있는 권한을 부여
      • 이렇게 해야 Jenkins 컨테이너 내부에서 Docker 소켓에 접근할 권한이 없다는 에러인 permission denied while trying to connect to the Docker daemon socket 가 안나온다.

5. Jenkins pipeline 본격적인 구축 시작

  • 우선 빌드 파이프라인에서 SSH 키를 사용해 원격 서버에 안전하게 접속할 수 있도록 도와주는 플러그인인 SSH Agent 플러그인 설치를 한다.
  • pipline 프로젝트 생성
  • 파이프라인 스크립트 작성 (딴거 다 필요없음) 
    pipeline {
    agent any
    
    environment {
        DOCKERHUB_CREDENTIALS = credentials('dockerhub_credentials') // Docker Hub 자격 증명 ID
        DOCKER_IMAGE_NAME = "youngsuoh/dr-rate-frontend" // Docker 이미지 이름
    }

    stages {
        stage('Checkout') {
            steps {
               git branch: 'main', credentialsId: 'git_credentials', url: 'https://github.com/BitCamp-Final-Project/Dr.Rate-Frontend.git' // GitHub 저장소 URL
            }
        }
        
        stage('Build Docker Image') {
            steps {
                script {
                    dockerImage = docker.build("${DOCKER_IMAGE_NAME}:${env.BUILD_ID}")
                }
            }
        }
        
        stage('Push to Docker Hub') {
            steps {
                script {
                    docker.withRegistry('https://registry.hub.docker.com', 'dockerhub_credentials') {
                        dockerImage.push()
                    }
                }
            }
        }
        
        stage('Deploy on NCP') {
            steps {              
            sh """
            ssh -i /var/jenkins_home/.ssh/jenkins_ncp_key -o StrictHostKeyChecking=no root@211.188.63.156 "
            docker pull ${DOCKER_IMAGE_NAME}:${env.BUILD_ID} &&
            docker stop container-name || true &&
            docker rm container-name || true &&
            docker run -d --name container-name \
              -p 80:80 -p 443:443 \
              -v /etc/letsencrypt/live:/etc/letsencrypt/live:ro \
              -v /etc/letsencrypt/archive:/etc/letsencrypt/archive:ro \
              ${DOCKER_IMAGE_NAME}:${env.BUILD_ID}
            "
            """
        
    }
}
    }
}

6. Jenkins가 NCP 서버에 SSH로 접근할 수 있도록 SSH 키를 준비

  • NCP에 공개키를 생성한다. 
    nano jenkins_ncp_key  // nano 후 키페어 내용 넣기
chmod 600 jenkins_ncp_key
ssh-keygen -y -f jenkins_ncp_key  // 공개키 발급
chmod 600 jenkins_ncp_key // 공캐키 권한 변경

docker cp jenkins_ncp_key jenkins:/var/jenkins_home/.ssh/jenkins_ncp_key // 젠킨스로 복사
  • pipeline 스크립트를 다음처럼 작성한다 
    ssh -i /var/jenkins_home/.ssh/jenkins_ncp_key -o StrictHostKeyChecking=no root@211.188.63.156
  • nano jenkins_ncp_key 를 통해 jenkins_ncp_key 파일을 열고, Jenkins 자격 증명으로 사용할 프라이빗 키를 직접 입력한다. 이때 프라이빗 키는 키페어 그대로 복붙하면 된다.
  • jenkins_ncp_key 파일의 권한을 설정한다. chmod 600 를 통해 파일 소유자(root)만 읽고 쓸 수 있도록 제한한다.
  • ssh-keygen -y -f jenkins_ncp_key 를 통해 jenkins_ncp_key 파일의 공개 키를 생성한다.
    • 다음의 형식으로 나오는데 복사를 해둬야 한다 
      ssh-rsa AAAAB3NzaC1yc2EAAAABIwAAAQEAvGz..
  • chmod 600과 chmod 700 명령어는 SSH 키 파일과 디렉토리의 보안을 강화하기 위해 설정한다.

Q) 공개 키와 비공개 키의 역할과 차이점은?

공개 키와 비공개 키의 역할

  1. 비공개 키 (Private Key):
    • Jenkins 서버에 저장되어 있으며, 외부에 노출되지 않는 개인 키
    • Jenkins가 NCP 서버에 접근할 때, 이 비공개 키로 서명을 만들어 인증을 요청한다.
    • 이 비공개 키는 Jenkins 서버의 자격 증명 관리(Credential)에 등록하여 Pipeline에서 사용되도록 설정된다.
  2. 공개 키 (Public Key):
    • 이 공개 키는 NCP 서버의 authorized_keys 파일에 저장된다.
    • NCP 서버는 Jenkins 서버가 접속을 시도할 때, 공개 키로 비공개 키 서명을 검증함으로써 Jenkins의 접속 요청을 허가한다.
    • 즉, 비공개 키와 공개 키가 일치할 때만 접근을 허용하여 보안적인 접속을 가능하게 한다.

공개 키 생성 이유

  • 자동화된 인증: Jenkins가 NCP 서버에 매번 비밀번호를 입력하지 않고 자동으로 배포를 수행할 수 있게한다.
  • 보안 강화: SSH 키 기반 인증은 비밀번호 인증보다 훨씬 보안성이 높기 때문에, 외부로부터의 불필요한 접근 시도를 차단할 수 있다.

비밀번호: root@211.188.51.105와 같이 비밀번호를 입력하라는 메시지는 일반적으로 SSH 연결을 위해 서버에서 요구하는 사용자 계정 비밀번호입니다. 이 비밀번호는 SSH 키 대신 계정 접근을 위해 입력하는 일반적인 비밀번호이다.
