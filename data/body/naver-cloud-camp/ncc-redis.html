💡 Redis는 Remote에 위치하고 프로세스로 존재하는 In-Memory 기반의 Dictionary 구조 데이터 관리 Server 시스템이다.

관계형 데이터베이스와 같이 쿼리 연산을 지원하지 않지만, 대신 데이터의 고속 일ㅇㄱ기와 쓰기에 최적화되어 있다. 일종의 NoSQL이다.

또한 Redis는 In-Memory 솔루션으로도 분류되기도 하는데, 다양한 데이터 구조체를 지원함으로써 DB, Cache, Message Queue, Shared Memory 용도로 사용될 수 있다.

일반 데이터 베이스 같이 디스크(SSD)에 데이터를 쓰는 구조가 아니라 메모리(dram)에서 데이터를 처리하기 때문에 작업 속도가 상당히 빠르다.

Redis는 기본적으로 1개의 싱글 쓰레드로 수행되기 때문에 안정적 인프라를 구축하기 위해서는 Replication(Master-Slave 구조) 필수이다.

Redis 활용하기 - 캐시(Cache)

서비스를 처음 운영할 땐, WEB - WAS - DB 정도로 작게 인프라를 구축하는데, 사용자가 늘어나면 DB에 무리가 가기 시작한다.

DB는 데이터를 물리 디스크에 직접 쓰기 때문에 서버에 문제가 발생해도 데이터가 손실되지 않지만, 매 트랜잭션마다 디스크에 접근해야 하므로 부하가 많아지면 성능이 떨어진다.

그래서 사용자가 늘어나면 DB를 스케일 인 또는 스케일 아웃하는 방식 외에도 캐시 서버를 검토하게 된다.

📄 DB 스케일 인 & 아웃

DB 스케일 인(Scale-In)과 스케일 아웃(Scale-Out)은 데이터베이스 시스템의 성능을 확장하거나 축소하는 전략을 의미해.

1. 스케일 아웃 (Scale-Out)

  • 정의: 데이터베이스의 성능을 확장하기 위해 서버(노드) 개수를 추가하는 방식이야. 여러 대의 서버가 클러스터를 구성하여 데이터와 트래픽을 분산 처리함으로써 부하를 분산하는 방법이야.
  • 장점:
    • 트래픽 증가에 따라 용량을 쉽게 확장할 수 있어.
    • 장애가 발생하더라도 다른 노드가 역할을 대신할 수 있는 고가용성을 제공해.
    • 분산 환경에 적합하며, 클라우드 기반 시스템에서 흔히 사용하는 방식이야.
  • 단점:
    • 데이터 일관성 관리가 어려울 수 있어(특히 분산 시스템에서).
    • 복잡한 분산 처리 로직이 필요할 수 있어.

2. 스케일 인 (Scale-In)

  • 정의: 반대로 서버(노드) 개수를 줄여서 리소스를 효율적으로 사용하는 방식이야. 필요하지 않은 노드를 제거함으로써 비용을 줄이는 방법이야.
  • 장점:
    • 불필요한 리소스를 줄여서 비용 효율을 극대화할 수 있어.
    • 관리가 쉬워져서 유지보수 비용이 감소해.
  • 단점:
    • 트래픽이 증가하면 성능 저하가 발생할 수 있어.
    • 감소된 용량으로 인해 장애 발생 시 대응이 어려울 수 있어.

Redis Cache는 메모리 단에 위치한다. 따라서 용량이 적지만 접근 속도가 빠르다.

다만 저장하려는 데이터 셋이 주어진 메모리 크기보다 크면 디스크를 쓰는 것이 올바른 선택이다.

Redis 캐시의 활용 사례

Twitter는 140자 정도의 짧은 글을 올릴 수 있는 SNS이다.

2012년 당시 Twitter는 초당 30만 건이 넘는 Timeline 요청이 발생했었다

Twitter의 데이터 센터에 존재하는 방대한 양의 Redis Cluster는 각 사용자의 Timeline에 노출될 Tweet의 정보(TweetId, 작성자 Id) 를 List 형태로 약 800개 정도 캐싱한다

발생하는 Timeline 요청은 바로 데이터베이스로 접근하지 않고 Redis에 캐싱된 Timeline 정보를 먼저 가져와서, 이를 토대로 Query를 단순화하여 데이터베이스에 접근하여 처리한다.

RAM은 휘발성인데 그러면 실행중인 Redis를 끄면 데이터가 전부 날라간다고 생각이 들게 되지만, Redis는 In-memory이지만 persistent on disk 데이터 베이스이기도 하다

Redis는 특정한 때에 현재까지의 in-memory 상태를 disk에 저장해 두었다가 Redis를 다시 시작했을 때, disk에 저장해두었던 dump 파일들을 load하기 때문에 데이터의 손실을 방지할 수 있다.

In-memory DB vs Disk based DB

  • 별도의 세션 스토리지를 구성하여 세션의 정합성 문제를 해결하려고 할 때, Session Storage를 이용하는 방법이 가장 이상적이다.
  • 그럼 세션 스토리지로서 적합한 데이터 베이스는 무엇일까?
  • 데이터베이스의 데이터가 어느 공간에 저장이 되는가에 따라서 in-memory DB와 Disk based DB로 분류된다.
  • 전자는 데이터를 메모리에 저장하여 관리하고, 후자는 데이터를 디스크에 저장하여 관리한다.
  • 우리가 만든 웹 서비스를 이용할 때, 비인가 사용자와 인가된 사용자 모두 접근할 수 있는 요청도 존재하고, 인가된 사용자만이 접근 가능한 요청도 존재할 것이다.
  • 이렇게 인가된 사용자만 접근할 수 있는 요청을 처리할 때마다 매번 세션 스토리지에서 해당 로그인 세션이 존재하는지 확인하는 작업을 진행해야 하기 때문에 성능에 악영향을 주지 않도록 빠르게 세션 정보를 찾아서 제공해야 한다.
  • Disk based DB는 디스크에서 데이터를 찾아 페이지 단위로 버퍼로 전송하는 시간이 발생하기 때문에 여러 I/O 작업 처리에 있어서 병목현상이 발생하게 된다.
  • 이러한 이유로 세션이 존재하는지 확인하는 작업을 여러번 반복해야 하는 서비스에서 세션 스토리지로 Disk based DB를 사용하는 것은 성능적인 측면에서 올바른 선택이 아니고 생각된다.
  • 반면, In-memory DB는 애초에 모든 데이터를 메모리에 저장하기 때문에 Disk I/O 작업이 발생할 일이 없다. 따라서 디스크 기반의 데이터베이스에서 발생하는 병목 현상을 피할 수 있다.
  • 그리고 세션은 HTTP의 비연결 지향과 stateless과 같은 특성을 보완하기 위해 사용하는 것이다.
  • 세션은 주로 로그인한 사용자의 정보를 저장하는데, 이 정보는 영원히 저장되어야 하는 정보가 아니다.
  • 거기다 세션에 데이터 유실로 발생하는 피해가 다른 데이터에 비해 적다. 극단적인 예로 세션 저장소의 데이터가 유실된다면 사용자는 재 로그인만 진행하면 된다.
  • 따라서 세션 스토리지로 in-memory DB의 사용이 적절하다.

Redis 데이터의 영속성 (Redis Persistence)

  • Redis는 In-memory DB임에도 불구하고, 메모리 데이터를 disk에 저장할 수 있는 특징이 있다.
  • 그래서 서버가 꺼진 후 restart되더라도, disk에 저장해놓은 데이터를 다시 읽어서 메모리에 로딩하기 때문에 데이터를 유실하지 않는다
  • 이런 영속성 기능은 휘발성 메모리 DB를 데이터 스토어로서 활용한다는 장점이 있지만, 이 기능 때문에 장애의 주 원인이 되기도 한다.
  • 그러므로 이 기능을 잘 알아보고 사용하는게 중요하다.

Redis의 저장 방식

redis에서는 데이터를 저장하는 방법이 RDB(snapshotting)방식과 AOF(Append Only File) 두 가지가 있다

  1. RDB 방식은 특정한 간격마다 메모리에 있는 Redis 데이터 전체를 디스크에 쓰는 것이다. (백업에 용이)
  2. AOF 방식은 명령이 실행될 때마다 데이터를 파일에 기록하여 데이터의 손실이 거의 없다.

1. RDB (snapshotting) 방식

  • Redis는 인메모리 데이터를 주기적으로 파일에 저장하는데, Redis 프로세스가 장애로 인해 종료되더라도 해당 파일을 읽어들이면 이전의 상태를 동일하게 복구할 수 있다
  • 우리가 직접 세팅하지 않더라도 자동으로 .rdb라는 확장자의 파일에 인메모리 데이터를 저장하도록 default 설정이 되어 있다.
  • RDB(snapshot)는 순간적으로 메모리에 있는 내용을 스냅샷을 떠서 DISK에 옮겨 담는 방식이다.
  • 스냅샷을 뜬다는 말은 특정 시점의 메모리에 있는 데이터를 바이너리 파일로 저장하는 뜻이다.
  • .rdb 파일은 AOF 파일보다 사이즈가 작다는 특징이 있다. 따라서 로딩 속도가 AOF보다 빠르다.
  • RDB 방식은 메모리의 snapshot을 그대로 저장하기 때문에 서버를 재구동시할 때 snapshot을 다시 읽으면 되므로 속도가 빠른 장점이 있다.
  • 그러나 snapshow을 추출하는데 시간이 오래 걸리고 도중에 서버가 꺼지면 이후의 데이터가 모두 사라진다는 단점이 있다.
  • 실제로 SAVE 옵션으로 50GB 의 메모리 상태를 저장한다면 7 ~ 8분 정도 소요된다고 한다.
  • RDB 설정하기
    • RDB 기능을 이용하려면 Redis 설정 파일인 redis.conf 파일에 다음과 같은 내용을 추가해야 한다. (윈도우에서는 redis-windows-service.conf를 수정하고 서비스 재시작하면 적용된다.)
  • 저장 시점 정기
    • RDB 저장 방식에는 SAVE와 BGSAVE 2가지가 있다.
    • SAVE는 순간적으로 redis의 동작을 정지시키고 그 snapshot를 디스크에 저장.(blocking 방식)
    • BGSAVE는 백그라운드 SAVE 라는 의미로 별도의 자식 프로세스를 띄운 후, 명령어 수행 당시의 snapshot을 disk에 저장하고, redis는 동작을 멈추지 않게 된다. (non-blocking 방식)
  • SAVE 조건은 여러 개를 지정할 수 잇고, 모두 or 조건이다.
  • 만약 RDB 저장을 사용하지 않으려면 redis.conf에서 SAVE를 모두 주석처리하면 된다.
  • BGSAVE 방식은 fork를 하기 때문에 메모리를 거의 2배 가량 사용하므로 이에 주의해야 한다.

save 900 1     # 900초(15분) 동안 1번 이상 key 변경이 발생하면 저장 
save 300 10    # 300초(5분) 동안 10번 이상 key 변경이 발생하면 저장 
save 60 10000  # 60초(1분) 동안 10000번 이상 key 변경이 발생하면 저장

2. AOF(Append Only File) 방식

  • AOF 방식은 redis의 모든 write/update 연산 자체를 모두 log파일에 기록하는 형태이다
  • defult로 appendonly.aof 파일에 기록되며, 조회를 제외한 CUD 명령어 실행될때마다 기록된다.
  • 그리고 서버가 재시작될 때, log에 기록된 write/update 연산을 재 실행하는 형태로 데이터를 복구하는 방식이다.

즉, 다음과 같은 순서로 데이터가 저장된다.

  1. 클라이언트가 Redis 에 업데이트 관련 명령을 요청한다.
  2. Redis 는 해당 명령을 AOF에 저장한다.
  3. 파일쓰기가 완료되면 실제로 해당 명령을 수행해서 Redis 메모리에 내용을 변경한다.

이처럼, operation이 발생할때 마다 매번 기록하기 때문, RDB 방식과는 달리 특정 시점이 아니라 항상 현재 시점까지의 로그를 기록할 수 있으며, 기본적으로 non-blocking 으로 동작 된다.

AOF는 log 파일에 대해서만 append하기 때문에 log write 속도가 빠르고 어떤 시점에 서버가 다운되더라도 데이터가 사라지지 않는 장점이 있다.

그러나, 모든 write/update 연산을 log파일에 남기기 때문에 log 데이터 양이 굉장히 크고 , 복구 시 저장된 모든 write/update연산을 다시 실행하기 때문에 재시작 속도가 느린 단점이 있다.

RDB와 AOF 방식 중 어느 방식을 채택하는가?

  • RDB (Redis Database File)
    • 특징: 일정한 시간 간격으로 데이터 스냅샷을 저장하는 방식. 저장된 스냅샷 파일은 백업에 유리함.
    • 장점:
      • 복구 속도가 빠르고, 스냅샷 파일은 다른 서버로 쉽게 복사 가능해 백업 및 복원에 용이.
      • Redis 서버의 성능에 미치는 영향을 최소화함. 스냅샷 생성 중에도 빠르게 작동.
    • 단점:
      • 스냅샷 간격 사이에 발생한 데이터는 유실될 수 있어, 데이터의 완전한 지속성 보장이 어려움.
    • 적합한 상황:
      • 데이터 유실을 어느 정도 감수할 수 있거나, Redis를 캐시 서버로 사용하는 경우.
      • 복구 시간이 짧아야 하고, 시스템 성능에 영향을 덜 미치고 싶을 때.
  • AOF (Append Only File)
    • 특징: 모든 쓰기 명령을 로그에 기록하여 지속적으로 데이터를 저장하는 방식.
    • 장점:
      • 데이터 복구 시 지속성 보장이 뛰어남. 거의 모든 데이터를 복구할 수 있음.
      • AOF 파일을 자동으로 리라이팅(정리)하여 파일 크기를 줄일 수 있음.
    • 단점:
      • 로그를 지속적으로 기록하므로 RDB보다 저장 성능에 부담이 큼.
      • 파일 크기가 커질 수 있고, 복구 시간이 RDB에 비해 오래 걸릴 수 있음.
    • 적합한 상황:
      • 데이터의 손실이 거의 없어야 하는 경우, 예를 들어, 중요한 데이터가 있는 세션 저장소나 트랜잭션 데이터를 다룰 때.
      • Redis를 기본 데이터 저장소로 사용하거나 데이터의 일관성이 중요한 경우.

결론

  • 고성능이 필요한 경우: RDB를 선택해 성능을 최적화하면서 데이터 유실에 대해 어느 정도 감수하는 편이 나아.
  • 데이터 안전이 우선일 때: AOF를 사용해 데이터 일관성과 복구 가능성을 높여.
  • 때로는 둘을 함께 설정해 RDB를 기본으로 두고 AOF를 보조 방식으로 사용해 데이터 손실을 최소화하면서도 성능을 유지할 수 있어.
