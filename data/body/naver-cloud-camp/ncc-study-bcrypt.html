1. 단방향 암호화

  • 단방향 암호화는 평문을 암호화 할 수는 있지만 암호화된 문자를 다시 평문으로 복호화가 불가능한 방식이다.
  • 주로 해시 알고리즘을 이용하여 단방향 암호화를 구현한다.
  • 단방향 암호화를 사용하는 주된 이유는 메시지 또는 파일의 무결성(integrity)을 보장하기 위해서다.
  • 원본의 값이 1bit라도 달라지게 된다면, 해시 알고리즘을 통과한 후의 해시값은 매우 높은 확률로 달라진다. 이를 통해 메시지나 파일의 원본 여부를 파악할 수 있다.

단방향 암호화의 한계

  • 해시 알고리즘은 동일한 평문에 대하여 항상 동일 해시값을 갖는다.
    • 따라서 특정 해시 알고리즘에 대해 특정 평문이 어떤 해시값을 갖는 지 알 수 있다.
  • 이런 특징을 이용하여 해시 함수의 해시 값들을 대량으로 정리한 테이블이 존재하는데, 이를 레인보우 테이블이라 부른다.
    • 그리고 레인보우 테이블을 이용해 사용자의 정보를 해킹하는 공격을 레인보우 공격이라고 한다.
  • 또한 해시 함수는 본래 데이터를 빠르게 검색하기 위해서 탄생됐다. 하지만 이러한 해시 함수의 빠른 처리 속도는 공격자에게 오히려 장점으로 작용된다.
    • 공격자는 매우 빠른 속도로 임의의 문자열의 해시값과 해킹할 대상의 해시값을 비교해 대상자를 공격할 수 있다. (MD5를 사용한 경우 일반적인 장비를 이용하여 1초당 56억 개의 해시값을 비교할 수 있다)

2. 솔팅(Salting) & 키 스트레칭(Key Stretching)

솔팅(Salting)

솔팅은 단방향 해시로 암호화를 진행할 시, 본래 데이터에 추가 랜덤 데이터를 더하여 암호화를 진행하는 방식이다. 추가 데이터가 포함 되었기 때문에 원래 데이터의 해시값에서 달라진다.

키 스트레칭(Key Stretching) → hash function을 여러 개 적용하는 방

단방향 해시값을 계산 한 후 그 해시값을 해시하고 또 이를 반복하는 방식이다.

최근에는 일반적인 장비로 1초에 50억 개 이상의 해시값을 비교할 수 있지만, 키 스트레칭을 적용하여 동일한 장비에서 1초에 5번 가량 비교할 수 있다. GPU(Graphics Processing Unit)를 사용하더라도 수백에서 수천 번 정도만 비교할 수 있다.

Bcrypt

Bcrypt는 비밀번호를 안전하게 암호화하기 위한 해시 함수로, 특히 보안성을 강화하기 위해 설계된 암호화 알고리즘이야. 비밀번호를 안전하게 저장하거나 검증하는 데 자주 사용돼. 아래에서 Bcrypt의 주요 특징과 사용 방법을 정리해볼게.

Bcrypt의 특징

  • 단방향 해시
    • 비밀번호를 암호화하면 복호화할 수 없고, 원래 값과 비교만 가능해.
    • 비밀번호 검증은 입력값을 다시 해싱한 결과를 기존 해시값과 비교하는 방식으로 이루어져.
  • Salt 사용
    • 같은 비밀번호라도 매번 다른 값으로 암호화되도록 **Salt(랜덤 데이터)**를 자동으로 추가해.
    • 이를 통해 무차별 대입 공격(Brute Force)이나 레인보우 테이블 공격을 방어할 수 있어.
  • 해시 속도 조절 가능
    • Work Factor 또는 Cost Factor를 조정해 해시 계산의 복잡도를 설정할 수 있어.
    • 값이 높을수록 암호화 속도가 느려지며, 이는 공격자를 방어하는 데 효과적이야.
  • Adaptive Algorithm(적응형 알고리즘)
    • 시간이 지나고 하드웨어 성능이 향상돼도, Work Factor를 높여 해싱 난이도를 조정 가능.

Bcrypt의 장점

  1. 강력한 보안
    • Salt로 인해 레인보우 테이블 공격이 불가능.
    • Work Factor로 계산 복잡도를 조정 가능.
  2. 사용 편의성
    • Salt를 자동으로 처리하므로 개발자가 별도로 관리할 필요 없음.
  3. Spring Security 통합
    • Spring Security에서 기본적으로 지원해 구현이 간단.

Bcrypt의 단점

  1. 비교적 느린 속도
    • 보안을 강화하기 위해 의도적으로 속도가 느리게 설계됨.
    • 다량의 비밀번호를 처리해야 하는 경우 성능 저하 가능성.
  2. 비대칭성
    • 복호화가 불가능하므로, 사용자가 비밀번호를 잊어버리면 복구가 불가능.

예시 코드

  • 단순 salting을 이용한 방법
public class BcryptExample {
    public static void main(String[] args) {
        BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder();

        // 비밀번호 암호화
        String rawPassword = "myPassword123";
        String encodedPassword = passwordEncoder.encode(rawPassword);

        System.out.println("암호화된 비밀번호: " + encodedPassword);

        // 비밀번호 검증
        boolean isMatch = passwordEncoder.matches(rawPassword, encodedPassword);
        System.out.println("비밀번호 일치 여부: " + isMatch);
    }
}

BCryptPasswordEncoder**를 사용하면 자동으로 Salting이 진행돼요. Bcrypt는 자체적으로 Salt를 생성하고, 암호화된 비밀번호에 이 Salt를 포함하기 때문에 별도로 Salt를 관리할 필요가 없다.

  • key-streching을 이용한 방법
    • Spring Security에서 제공하는 BCryptPasswordEncoder는 기본적으로 키 스트레칭 기능을 포함하고 있어. Cost Factor를 조정하면 비밀번호 해싱의 반복 횟수를 설정할 수 있어.
public class KeyStretchingExample {
    public static void main(String[] args) {
        // Cost Factor 설정 (10 이상이 적절)
        int costFactor = 12; // 반복 횟수는 2^12 = 4096번
        BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder(costFactor);

        // 비밀번호 암호화
        String rawPassword = "mySecurePassword";
        String encodedPassword = passwordEncoder.encode(rawPassword);

        System.out.println("암호화된 비밀번호: " + encodedPassword);

        // 비밀번호 검증
        boolean isMatch = passwordEncoder.matches(rawPassword, encodedPassword);
        System.out.println("비밀번호 일치 여부: " + isMatch);
    }
}

Cost Factor의 의미

  • Cost Factor가 12라면, 해싱 연산이 2^12 = 4096번 반복돼.
  • Cost Factor가 높아질수록 연산 속도가 느려져 공격자가 해싱 결과를 대입하는 데 더 많은 시간이 걸려.

해시 테이블 크기와 무결성

해시 테이블의 크기는 암호화 알고리즘의 종류와 설정에 따라 다르지만, 무결성 보장과 보안성은 해시 테이블의 크기뿐만 아니라 해시 알고리즘의 설계와 충돌 회피 능력에 크게 좌우돼.

아래에서 주요 암호화 해시 함수의 결과 크기와 무결성 보장에 대해 설명할게.

  1. 해시 출력 크기
    1. 해시 함수는 고정된 크기의 출력(다이제스트)을 생성해.
      • MD5: 128비트 (16바이트)
      • SHA-1: 160비트 (20바이트)
      • SHA-256: 256비트 (32바이트)
      • Bcrypt: 일반적으로 184비트 정도
      • Argon2: 설정에 따라 다르지만, 보통 256비트 이상
    • 해시 출력의 크기가 클수록 충돌 가능성(서로 다른 입력이 같은 해시 값을 가지는 경우)이 낮아지고, 무결성 보장이 더 강해져.
  2. 충돌 가능성과 보안
    1. 해시 함수는 이론적으로 무한한 입력 값을 고정된 크기로 변환하므로 충돌 가능성이 있어.
    2. 하지만 현대적인 해시 알고리즘은 충돌 가능성을 극도로 낮게 설계해
      1. SHA-256: 2¹²⁸(약 3.4x10³⁸)번의 시도를 해야 충돌 가능성이 생길 정도로 설계됨.
      2. 즉, 충분히 큰 해시 크기를 가진다면 실질적으로 충돌 가능성은 무시할 수 있어.

2. 충돌 가능성과 보안

  • 해시 함수는 이론적으로 무한한 입력 값을 고정된 크기로 변환하므로 충돌 가능성이 있어.
  • 하지만 현대적인 해시 알고리즘은 충돌 가능성을 극도로 낮게 설계해:
    • SHA-256: 2¹²⁸(약 3.4x10³⁸)번의 시도를 해야 충돌 가능성이 생길 정도로 설계됨.
    • 즉, 충분히 큰 해시 크기를 가진다면 실질적으로 충돌 가능성은 무시할 수 있어.

3. 무결성을 보장하기 위한 해시 크기

  • 무결성 보장은 출력 크기뿐 아니라 알고리즘의 충돌 저항성과 암호화 강도에 의해 달성돼.
  • 예를 들어:
    • SHA-256: 현재로선 매우 안전하며, 데이터의 무결성을 보장할 수 있음.
    • SHA-1: 이미 충돌 공격이 가능하므로 무결성 보장에 적합하지 않아.

해시 크기와 저장소 고려

1. 해시 테이블 저장소 크기

  • 해시 크기가 클수록 데이터베이스나 저장소의 사용량이 늘어나지만, 실제로 출력 크기가 256비트(32바이트)인 SHA-256 정도면 충분히 현실적으로 사용 가능해.
  • 예를 들어:
    • 사용자가 1백만 명이고, 각각의 비밀번호를 SHA-256으로 저장한다면:
      • 필요 저장소 = 1,000,000 × 32바이트 ≈ 32MB
      • 이는 현대 시스템에서 무시할 수 있는 수준.

2. Bcrypt 출력 크기

  • Bcrypt의 암호화 결과는 Salt와 해시를 포함하므로 보통 60~72자의 문자열(184비트 정도)을 저장.
  • 저장소 크기 예시:
    • 사용자가 1백만 명이라면:
      • 필요 저장소 ≈ 1,000,000 × 72바이트 ≈ 72MB
      • 마찬가지로 현대 시스템에서 충분히 처리 가능한 수준.

비밀번호 무결성 보장을 위한 핵심 요소

  1. 알고리즘 선택
    • MD5나 SHA-1은 충돌 공격에 취약하므로, SHA-256이나 Bcrypt를 사용해야 무결성을 보장할 수 있어.
  2. Salt 적용
    • Salt를 사용하면 동일한 비밀번호라도 다른 해시 값이 생성되므로 무결성이 더 강화돼.
  3. 충분한 해시 출력 크기
    • 256비트 이상(예: SHA-256)은 실질적으로 충돌을 방지하는 데 충분해.
  4. 키 스트레칭
    • 키 스트레칭을 적용해 암호화 연산을 반복하면 공격자의 무차별 대입 속도가 느려져 보안성이 높아져.

1명당 32바이트 계산 예시

1명의 비밀번호를 SHA-256으로 암호화한 경우, 데이터베이스에 저장해야 하는 값은 32바이트.

  • 만약 사용자 1명당 비밀번호 해시 값만 저장한다면: 
    사용자 수 × 32바이트 = 총 필요 저장소
  • 예:
    • 10명: 10 × 32 = 320바이트
    • 1,000명: 1,000 × 32 = 32,000바이트 (32KB)
    • 1,000,000명: 1,000,000 × 32 = 32,000,000바이트 (32MB)

Salt 사용 시의 저장소 요구량

SHA-256에 Salt를 추가하면, Salt 값도 저장해야 하므로 저장소 요구량이 늘어나.

  1. Salt 크기 설정
    • 일반적으로 Salt는 16~32바이트 크기를 사용해.
    • SHA-256 출력 크기(32바이트) + Salt 크기(예: 16바이트)를 더하면 1명당 저장소 요구량은 48바이트.
  2. Salt 포함 계산 
    사용자 수 × (해시 크기 + Salt 크기) = 총 필요 저장소
    • 예: Salt가 16바이트일 때
      • 1,000,000명: 1,000,000 × (32 + 16) = 48,000,000바이트 (48MB)
