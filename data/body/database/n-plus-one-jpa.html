N+1 문제는 연관관계가 있는 엔티티를 조회할 때, 처음 조회(1번) 이후 연관 엔티티를 가져오기 위한 쿼리가 결과 건수(N번)만큼 추가로 발생하는 현상이다. Spring Data JPA/Hibernate에서 가장 흔하게 만나는 성능 이슈다.

왜 발생하는가

영속성 컨텍스트는 연관 엔티티를 프록시(LAZY)로 채워두고, 실제 접근 시점에 별도 SELECT로 초기화한다. 리스트를 순회하며 연관 필드에 접근하면 컬렉션 크기만큼 개별 쿼리가 나간다.

public interface OrderRepository extends JpaRepository<Order, Long> {
}

// Service
List<Order> orders = orderRepository.findAll(); // 쿼리 1번

for (Order order : orders) {
    order.getMember().getName(); // 컬렉션 순회마다 쿼리 발생 (N번)
}
SELECT * FROM orders;

SELECT * FROM member WHERE id = 1;
SELECT * FROM member WHERE id = 2;
SELECT * FROM member WHERE id = 3;
-- ... N번 반복

EAGER도 안전하지 않다

JPQL은 작성된 문자열 그대로 SQL로 번역된다. "SELECT o FROM Order o"에는 member 언급이 없으므로 fetch 설정과 무관하게 orders만 SELECT하는 쿼리 한 줄이 만들어진다.

대신 EAGER는 getResultList()가 리턴되기 전, 각 로우를 엔티티 객체로 만드는 순간에 개입한다. Hibernate가 로우 하나를 Order 엔티티로 만들면서 "member가 EAGER네" 하고 그 자리에서 바로 SELECT * FROM member WHERE id = ?를 쏘고, 이걸 orders 개수만큼 반복한다. 즉 order.getMember()를 호출하는 게 아니라 orders를 조회받는 그 한 줄에서 이미 N번의 쿼리가 다 나가 있다는 뜻이다. (LAZY는 이 시점엔 프록시만 넣어두고, 실제 getMember() 호출 시점까지 미룬다.)

결국 EAGER는 fetch join처럼 한 방 쿼리를 만드는 게 아니라 "조회 즉시 LAZY 초기화를 대신 해주는 것"뿐이라 N+1은 그대로다. 게다가 getMember() 호출부에서 원인을 짚을 수 있는 LAZY와 달리 쿼리가 언제 왜 나가는지 추적하기 더 어려워지므로, 실무에서는 기본을 LAZY로 두고 필요할 때만 fetch join/EntityGraph로 명시하는 게 정석이다.

@ManyToOne(fetch = FetchType.EAGER)
private Member member;

// JPQL
List<Order> orders = em.createQuery("SELECT o FROM Order o", Order.class)
        .getResultList();
// EAGER여도 fetch join이 아니므로 N+1 그대로 발생
-- 1) JPQL 그대로 번역된 조회 쿼리 (member 언급 없음)
SELECT * FROM orders;

-- 2) getResultList() 리턴 전, 엔티티 매핑 중 EAGER라서 즉시 발행
SELECT * FROM member WHERE id = 1;
SELECT * FROM member WHERE id = 2;
SELECT * FROM member WHERE id = 3;
-- LAZY라면 이 쿼리들은 getMember() 호출 시점까지 미뤄질 뿐

해결 방법 1 — Fetch Join

JPQL에서 JOIN FETCH로 연관 엔티티를 한 번의 쿼리로 함께 가져온다. 가장 확실하고 흔히 쓰는 방법이다.

public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("SELECT o FROM Order o JOIN FETCH o.member")
    List<Order> findAllWithMember();
}
SELECT o.*, m.*
FROM orders o
JOIN member m ON o.member_id = m.id;

주의할 점 1 — 컬렉션 fetch join + 페이징 (HHH000104)

@OneToMany를 fetch join하면 SQL은 order 1개당 orderItem N개만큼 로우가 곱해져서 나온다(카티션 곱). 이 상태에서 SQL의 LIMIT/OFFSET으로 페이징하면 한 order의 item 로우들이 중간에 잘릴 수 있어서, DB 레벨 페이징 자체가 불가능하다. 그래서 Hibernate는 페이징 조건을 SQL에 내리지 않고 연관 데이터를 전부 메모리로 가져온 다음 애플리케이션에서 잘라내는 방식으로 우회하는데, 이때 HHH000104: firstResult/maxResults specified with collection fetch; applying in memory! 경고가 뜬다. 결과적으로 "1페이지만 보고 싶다"고 요청해도 테이블 전체를 메모리에 올리게 되므로 데이터가 크면 OOM으로 이어진다.

-- order 1건 + item 3건 → 3로우로 뻥튀기됨, 여기서 LIMIT을 걸 수 없는 이유
SELECT o.*, i.*
FROM orders o
JOIN order_item i ON i.order_id = o.id;
-- order_id=1, item_id=1
-- order_id=1, item_id=2
-- order_id=1, item_id=3   (LIMIT 2를 걸면 order 1의 item이 잘려버림)

그래서 컬렉션 + 페이징이 동시에 필요하면 fetch join 대신 아래 해결 방법 3(Batch Size)을 쓰는 게 정석이다. Order만 페이징 쿼리로 가져오고, orderItem은 IN 절 배치 조회로 별도 처리하면 카티션 곱 자체가 생기지 않는다.

주의할 점 2 — 컬렉션 fetch join 2개 이상 (MultipleBagFetchException)

한 엔티티에서 서로 다른 컬렉션 두 개(예: orderItems, coupons)를 동시에 fetch join하면, SQL 조인 결과는 두 컬렉션 크기의 곱만큼 로우가 생긴다. item 3개 × coupon 2개면 6로우가 나오는데, Hibernate 입장에서는 이 6로우를 다시 "item 3개, coupon 2개"로 정확히 되돌릴 방법이 없다(어떤 조합이 중복으로 뻥튀기된 건지 구분 불가). 그래서 Hibernate는 이걸 조용히 틀리게 조립하는 대신 MultipleBagFetchException을 던져서 애초에 막아버린다.

// 예외 발생: List(Bag) 컬렉션 2개를 동시에 fetch join
@Query("SELECT o FROM Order o JOIN FETCH o.orderItems JOIN FETCH o.coupons")
List<Order> findAllWithItemsAndCoupons();
// org.hibernate.loader.MultipleBagFetchException: cannot simultaneously fetch multiple bags
  • 컬렉션 타입을 List → Set으로 변경 — Hibernate가 중복 로우를 식별해서 걸러낼 수 있어 예외 없이 동작한다. 단 순서 보장이 없어지고, 데이터가 크면 여전히 카티션 곱만큼 메모리를 쓴다.
  • 컬렉션 하나만 fetch join, 나머지는 Batch Size로 — 한 쿼리에서는 최대 하나의 컬렉션만 fetch join하고, 나머지 컬렉션은 @BatchSize로 별도 IN 조회하게 둔다. 가장 무난한 선택.
  • 쿼리를 분리 — orderItems용 쿼리, coupons용 쿼리를 따로 날리고 애플리케이션에서 조합한다.

해결 방법 2 — @EntityGraph

JPQL을 직접 작성하지 않고, 특정 메서드에서만 연관 엔티티를 함께 로딩하도록 선언적으로 지정할 수 있다.

public interface OrderRepository extends JpaRepository<Order, Long> {

    @EntityGraph(attributePaths = {"member"})
    @Query("SELECT o FROM Order o")
    List<Order> findAllWithMember();

    // 메서드 이름 쿼리에도 적용 가능
    @EntityGraph(attributePaths = {"member"})
    List<Order> findByStatus(String status);
}

해결 방법 3 — Batch Size (in 절 배치 조회)

연관 엔티티 조회를 N번의 개별 쿼리 대신, IN 절 하나로 묶어서 가져오는 방식이다. fetch join과 달리 LAZY는 그대로 유지하면서 초기화 시점에 나가는 쿼리의 개수만 줄이는 방식이라, 컬렉션 fetch join이 페이징과 함께 못 쓰이는 문제(위 HHH000104)를 우회할 때 많이 쓴다.

동작 원리 — LAZY 프록시는 실제로 접근되는 순간 초기화되는데, 이때 Hibernate는 "그 프록시 하나만" 조회하는 게 아니라 같은 영속성 컨텍스트 안에 아직 초기화 안 된 동종 프록시들을 최대 size개까지 모아서 한 번의 IN 쿼리로 함께 초기화한다. 즉 반복문에서 order.getMember()를 처음 호출하는 순간, 그 컨텍스트에 이미 로딩되어 있던 다른 order들의 member 프록시 ID까지 긁어모아 IN (1, 2, 3, ...) 한 방으로 끝낸다. 그래서 fetch join처럼 처음부터 조인하는 게 아니라 "필요해지는 첫 접근 시점에, 한꺼번에 처리"하는 방식이다.

@Entity
public class Order {

    @ManyToOne(fetch = FetchType.LAZY)
    @BatchSize(size = 100)
    private Member member;
}

// Service
Page<Order> orders = orderRepository.findAll(pageable); // orders 100건 조회 쿼리 1번

for (Order order : orders) {
    order.getMember().getName(); // 처음 호출 시 member 프록시 100개를 한 번에 IN 조회
}
-- 1) 페이징 쿼리로 order 100건 조회
SELECT * FROM orders LIMIT 100 OFFSET 0;

-- 2) 첫 getMember() 호출 시, 컨텍스트에 쌓인 미초기화 member 100개를 한 번에 조회
SELECT * FROM member WHERE id IN (1, 2, 3, ..., 100);

@OneToMany 컬렉션에도 동일하게 적용된다 — 컬렉션에 @BatchSize를 붙이면, order 하나의 orderItems에 처음 접근할 때 다른 order들의 FK까지 모아서 WHERE order_id IN (...)로 한 번에 가져온다. fetch join처럼 카티션 곱이 생기지 않으므로 MultipleBagFetchException이나 페이징 문제 없이 컬렉션 2개 이상도 각각 배치로 안전하게 초기화할 수 있다.

@Entity
public class Order {

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @BatchSize(size = 100)
    private List<OrderItem> orderItems;
}
-- order_id 100건에 대한 orderItem을 한 번에 조회
SELECT * FROM order_item WHERE order_id IN (1, 2, 3, ..., 100);
# application.yml — 전역 설정 (엔티티/필드별 @BatchSize가 없으면 이 값이 기본 적용됨)
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100

size 값 정하기

  • size보다 데이터가 많으면 그만큼 나눠서 반복된다 — 예를 들어 order가 250건인데 size=100이면 IN 쿼리가 ceil(250/100) = 3번 나간다. N번보다는 훨씬 적지만 완전히 1번은 아니라는 점을 기억해야 한다.
  • 페이징을 함께 쓴다면 페이지 크기와 맞추는 게 기본이다(위 예시처럼 페이지 100건 + size=100이면 IN 쿼리 1번으로 끝난다).
  • 너무 크게 잡으면 필요 없는 데이터까지 IN 절에 물려서 파라미터 개수 제한(DB/드라이버마다 상이)에 걸리거나 실행계획이 나빠질 수 있으므로, 보통 100~1000 사이에서 실제 페이지/조회 단위에 맞춰 조정한다.

해결 방법 4 — DTO 직접 조회

연관 엔티티 전체가 필요한 게 아니라 화면에 필요한 필드 몇 개뿐이라면, 애초에 JOIN으로 DTO를 바로 조회해 N+1 자체를 없앨 수 있다.

@Query("""
    SELECT new com.example.dto.OrderResponse(o.id, m.name, o.totalAmount)
    FROM Order o
    JOIN o.member m
    """)
List<OrderResponse> findOrderResponses();

어떤 방법을 언제 쓸까

  • 단건/소수 연관 엔티티, 페이징 없음 → Fetch Join 또는 @EntityGraph
  • 컬렉션 연관관계 + 페이징 필요 → Batch Size (default_batch_fetch_size)
  • 조회 전용 API, 필요한 필드만 응답 → DTO 직접 조회

N+1 발생 여부 확인하기

운영에서 발견하기 전에 로컬/테스트 단계에서 쿼리 개수를 확인하는 습관이 중요하다.

spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
        show_sql: true
logging:
  level:
    org.hibernate.SQL: debug
    org.hibernate.orm.jdbc.bind: trace

테스트에서는 hibernate-p6spy나 Spring Data JPA의 @DataJpaTest + 쿼리 카운트 검증 방식으로 회귀를 막을 수 있다.
