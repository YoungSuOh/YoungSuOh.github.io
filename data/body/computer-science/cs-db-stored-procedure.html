Stored Procedure
데이터베이스에 저장된 SQL 쿼리들의 집합. 마치 하나의 함수처럼 실행하기 위한 쿼리 집합

왜 사용하는가?

  • 여러 줄의 쿼리문을 한 번의 요청으로 실행
  • 인자만 바뀌고 동일한 로직의 복잡한 쿼리를 매번 작성하는 비효율 해결

구조

DELIMITER $$

CREATE PROCEDURE 프로시저명 (매개변수)
BEGIN
    -- SQL Statements
END $$

DELIMITER ;
DELIMITER
프로시저 정의 끝 구분을 위해 사용
IN
호출 시 값 전달만
OUT
프로시저 내에서 값 설정해 반환
INOUT
값을 전달받고 수정된 값을 반환

사용 사례

1. 반복적인 조회 작업

CREATE PROCEDURE GetCustomerInfo(IN customerId INT)
BEGIN
    SELECT * FROM Customers WHERE id = customerId;
END $$

CALL GetCustomerInfo(5);

2. 데이터 삽입 + 로그 기록

CREATE PROCEDURE InsertOrder(IN customerId INT, IN productId INT, IN quantity INT)
BEGIN
    INSERT INTO Orders(customer_id, product_id, quantity, order_date)
    VALUES (customerId, productId, quantity, NOW());

    INSERT INTO Logs(action, log_time)
    VALUES ('New order added', NOW());
END $$

장단점

트래픽 감소
SQL이 서버에 저장됨 → 네트워크 트래픽 감소
재사용
한 번 작성하면 여러 앱·사용자가 재사용
성능 향상
최초 실행 시 컴파일 후 캐시. 다음 실행부터 빠름
보안
참조 중인 테이블 접근 차단 가능
호환성
SQL/PSM 표준 호환성 낮음, 재사용성 나쁨
성능
문자/숫자 연산은 C, Java보다 느림
디버깅
에러 위치 추적 어려움
