가비지 컬렉션 (Garbage Collection)

자바 이전에는 프로그래머가 모든 프로그램 메모리를 관리했음 → new delete를 통해 할당 & 해제.

하지만, 자바에서는 JVM이 프로그램 메모리를 관리한다.

JVM은 가비지 컬렉션이라는 프로세스를 통해 메모리를 관리한다. 가비지 컬렉션은 자바 프로그램에서 사용되지 않는 메모리를 지속적으로 찾아내서 제거하는 역할을 한다.

Reachability Analysis

GC는 단순히 "참조 횟수"로 객체를 제거하지 않는다.

대신 Reachability Analysis 알고리즘을 사용한다.

GC Root에서 도달 가능한 객체는 살아있는 객체로 판단한다.

GC Root의 대표적인 예시는 다음과 같다.

  • Stack의 지역 변수
  • static 변수
  • 실행 중인 Thread
  • JNI Reference

✅ 예시

User user = new User();
  • user 참조 변수는 Stack에 저장되고
  • 실제 User 객체는 Heap에 생성된다.
  • 메서드 실행 중에는 Stack에서 Heap 객체를 참조하고 있으므로 해당 객체는 reachable 상태
  • 하지만 메서드가 종료되면 Stack Frame이 제거되고 참조가 사라진다 ⇒ GC Root로부터 접근할 수 없는 객체 → GC 대상

Garbage Collection 동작 과정

Generational GC

대부분의 객체는 생성된 직후 빠르게 사라진다.

이를 Weak Generational Hypothesis라고 한다. 예를 들어 요청 처리 중 잠깐 생성되는 DTO, String, List 같은 객체들은 메서드가 끝나면 거의 대부분 필요 없어지기 때문에 오래 살아남지 않는다.

JVM은 이 특성을 활용해 Heap을 두 개의 큰 영역으로 나눈다.

  • Young Generation — 새로 생성된 객체가 저장되는 영역
  • Old Generation — 여러 번 GC를 통과하며 오래 살아남은 객체가 저장되는 영역

이 구조 덕분에 대부분의 "짧은 생명" 객체를 빠르게 정리할 수 있다.

1️⃣ Young Generation

Young Generation은 새 객체가 처음 생성되는 공간이다. 내부적으로 다음과 같이 구성된다.

Young Generation
├── Eden
├── Survivor 0 (S0)
└── Survivor 1 (S1)
  • Eden — 새 객체가 처음 생성되는 영역
  • Survivor 0, Survivor 1 — 살아남은 객체를 번갈아 저장하는 영역

✅ Young Generation의 객체 이동 과정

  1. 객체 생성 → Eden 저장
  2. Eden 가득 참 → Minor GC 수행
  3. 살아남은 객체 → To Survivor 이동 
    Eden → Survivor (age = 1)
  4. 다음 Minor GC는 Eden과 From Survivor를 검사한다. → 살아남은 객체는 To Survivor로 다시 복사된다. 
    Survivor → 다른 Survivor (age = 2)
  5. 여러 번 살아남음
  6. 일정 나이(age) 이상이면 Old Generation으로 Promotion 
    age >= threshold
→ Old Generation

-XX:MaxTenuringThreshold=15 // 기본적으로 최대 15번까지 Survivor를 거칠 수 있다.

✅ Minor GC — Young Generation만 대상으로 수행되는 GC

📌 동작 과정

  1. Eden과 현재 Survivor 영역을 검사
  2. Reachable 객체만 다른 Survivor로 복사
  3. age 증가
  4. 일정 조건 충족 시 Old Generation으로 Promotion
  5. 기존 Young 영역 메모리 재사용

📌 특징

  • 매우 자주 발생
  • 비교적 빠름
  • 대부분의 객체가 즉시 제거됨

✅ Survivor 영역

Survivor는 To Survivor, From Survivor 2가지로 존재.

Survivor는 다음 2가지 역할을 한다.

  1. 살아남은 객체를 임시 보관
  2. 객체의 나이(age)를 증가시키며 장수 여부 판단

🤔 왜 필요한가?

객체를 Eden에서 바로 Old Generation으로 보내면 문제가 생긴다.

  • 예시 — HTTP 요청 처리 중 생성되는 객체들은 잠깐 살아있다가 곧 사라질 수 있다. 
    요청 시작
→ DTO 생성
→ Service 처리
→ 응답 생성
→ 요청 종료
    • 이 객체들은 몇 번의 Minor GC를 통과할 수 있지만 결국 금방 사라진다.
    • 이런 객체를 바로 Old로 보내면
      • Old Generation이 빠르게 증가
      • Major GC 빈도 증가
      • Pause Time 증가
      • 따라서 JVM은 "조금 더 살아있는지 몇 번 확인한 뒤, 정말 오래 사는 객체만 Old로 보내자"

From/To Survivor 예시

// 첫 번째 Minor GC
Eden (alive objects)
   ↓
Survivor 0 (age = 1)

// 2번째 Minor GC
Eden + Survivor 0
   ↓
Survivor 1 (age = 2)

// 3번째 Minor GC
Eden + Survivor 1
   ↓
Survivor 0 (age = 3)
  • 이처럼 두 Survivor는 번갈아 사용된다.
  • 객체 Age는 Minor GC를 통과할 때마다 증가한다.

SurvivorRatio

  • Young Generation 내 비율을 조정하는 옵션. 
    -XX:SurvivorRatio=8 // 일반적으로 Eden : S0 : S1 = 8 : 1 : 1 정도로 구성된다.

2️⃣ Old Generation

Old Generation은 여러 번 Minor GC를 통과하며 오래 살아남은 객체를 저장하는 영역이다.

Young Generation에서 여러 번의 Minor GC를 거쳐 age threshold에 도달하게 되면 Old Generation으로 Promotion으로 승격된다.

✅ 특징

항목설명
저장 대상오래 살아남은 객체
크기Young보다 일반적으로 큼
수집 빈도낮음
수집 비용높음
Pause Time길어질 수 있음

주로 다음과 같은 "오래 살아남는 객체"를 저장한다.

  • Spring Singleton Bean
  • 캐시 데이터
  • 세션 정보
  • static 컬렉션

✅ Major GC

Old 영역이 부족해지면 Old Generation을 정리하는 GC가 발생한다.

이를 보통 Major GC라고 부른다.

✅ Compaction (압축)

Old Generation은 객체가 오래 머무르기 때문에 중간중간 빈 공간이 생긴다.

[객체][빈칸][객체][빈칸][객체]

이를 Fragmentation(단편화)라고 한다.

Compaction 후:

[객체][객체][객체][빈칸][빈칸]

⚠️ Old Generation이 가득 차면 발생하는 문제

Full GC

Full GC는 Heap 전체(Young Generation + Old Generation)를 대상으로 수행하는 GC이다.

가장 비용이 큰 이벤트 중 하나이다.

✅ Full GC가 하는 일

  1. GC Root 탐색
  2. Heap 전체 객체 Mark
  3. Unreachable 객체 제거
  4. 객체 이동 (Compaction)
  5. 단편화 (Fragmentation) 정리

Heap 전체를 다루기 때문에

  • 처리해야 할 객체 수가 많고
  • 메모리 이동 비용이 크며
  • 애플리케이션이 멈추는 시간이 길어질 수 있다.

✅ Stop-The-World (STW)

Full GC가 실행되는 동안 대부분의 어플리케이션 스레드는 일시 중단된다.

이 시간이 길어지면

  • API 응답 지연
  • 타임아웃
  • Kafka Consumer 지연
  • WebSocket 끊김

같은 문제가 발생할 수 있다.

✅ Full GC 발생 원인

  1. Old Generation 공간 부족 — 오래 살아남은 객체가 많아 Old 영역이 꽉 찬 경우
  2. Promotion Failure — Young에서 살아남은 객체를 Old로 이동할 공간이 부족한 경우
  3. Memory Leak — 사용되지 않지만 계속 참조되는 객체가 누적되는 경우
